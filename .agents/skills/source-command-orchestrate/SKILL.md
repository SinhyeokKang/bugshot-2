# source-command-orchestrate

Use this skill when the user asks to run the migrated source command `orchestrate`.

## Command Template

배치 계획 문서(예: `/audit` 결과를 쪼갠 `docs/features/<slug>/tasks.md`) 하나를 **여러 워커 세션에 나눠 태우고**, 이 세션은
**지휘만** 한다 — 브리프 작성 · 결정 수집 · 리뷰 · dev 통합 · push · 런타임 검증 · 이슈 라우팅 · 정리. 구현은 워커가 `/ship bypass`로 한다.

> **⚠️ 끝은 dev다.** `/ship`과 같다 — `/merge`(프로덕션)는 부르지 않는다. main 반영은 사용자가 `/merge`를 부를 때만이다.
>
> **⚠️ 지휘자는 코드를 고치지 않는다.** 이 세션이 쓰는 것은 브리프·`orch.md`·계획 문서의 체크·통합 커밋(cherry-pick)·문서 신선도 커밋뿐이다.
> 결함은 그 배치를 소유한 워커 세션으로 돌려보낸다 — 지휘자가 직접 고치면 워커의 컨텍스트와 리뷰 게이트를 건너뛴다.

malmoi `/orchestrate`(2026-09-24 출시 전 감사, 워커 13개·이슈 16건에서 틀려본 뒤 적은 규칙)를 BugShot 하네스에 맞게 옮긴 것이다.
DB·dev 서버가 없고 e2e 차단 게이트가 CI 단독이라는 두 가지가 다르다.

## 사용

- `/orchestrate <계획 문서 경로>` — 계획 문서의 배치를 전부 태운다.
- `/orchestrate <계획 문서> <배치...>` — 지정 배치만.

지휘자는 Claude Code·Codex 어느 쪽이든 된다(Codex는 `.agents/skills/source-command-<name>/SKILL.md`로 하위 스킬을 읽는다). 워커는 지휘자와 **같은 패밀리** 안에서 띄운다 — 구현·리뷰·검증·수정 라운드 모두 같은 경계다.

| 지휘자 | 허용 워커 런타임 / 모델 패밀리 |
|---|---|
| Claude Code | Claude Code / Sonnet·Opus |
| Codex | Codex / 현재 런타임이 제공하는 모델 |

**패밀리 교차는 사용자의 명시 허가가 있을 때만** 한다 — 잔여 토큰·도구 부재·속도를 이유로 임의로 교차하지 않는다. 허가한 범위는 `orch.md` 결정 기록에 남긴다.

## 0. 인테이크 (워커를 띄우기 전)

1. **`orch.md`에 지휘 계획을 먼저 쓴다.** 기능 폴더라면 `docs/features/<slug>/orch.md`, 그 밖에는 입력 계획 문서와 같은 디렉터리에 둔다. 원본 prd·design·tasks는 가리키고 복제하지 않는다. 담는 것: 착수 범위·시작 dev 해시, 결정 기록, 배치별 항목·파일 소유권·선행 관계·모델/effort·검증 게이트·상태, 파일 겹침 행렬과 병렬/직렬 순서. 이미 있으면 현재 진행 상태를 읽어 갱신한다.
2. **결정을 먼저 전부 받는다.** 해석이 갈리는 곳을 현재 런타임의 질문 도구로 **하나씩** 묻고(추천 하나 + 이유), 답을 `orch.md`의 "결정 기록"에 적는다. 워커가 도중에 결정 지점에서 멈추면 병렬이 직렬이 된다.
   - 설계가 필요한 배치는 `/feature` → `/feature-review`를 이 세션에서 먼저 돈다(워커가 계획 원본으로 쓴다).
3. **배치마다 워커 모델·effort를 정해 배치 표에 적는다.** 단순·기계적 구현은 가벼운 모델(Claude면 Sonnet), 불변식 판단이 무거운 배치(제출 어댑터·스토리지·issue 목록 병합·cascade 판정·selector 생성·pre-arm 그래프)와 독립 리뷰는 무거운 모델(Claude면 Opus)을 우선한다. effort는 현재 런타임이 지원하는 범위에서 고르고 선택 이유를 한 줄 적는다.
4. **파일 겹침 행렬로 병렬/직렬을 가른다.** 두 배치가 같은 파일을 고치면 병렬로 띄우지 않는다 — 선행이 dev에 들어간 뒤 후행을 띄우거나, 후행 브리프에 "겹치는 파일을 건드리기 전에 멈추고 `WAITING FOR <X>`를 보고하라, 신호를 받으면 `git rebase dev`"를 넣는다.
   ⚠️ **거의 모든 배치가 건드리는 핫스팟** — 겹침 판정에서 빠뜨리지 않는다:
   - i18n 사전 3벌: `src/i18n/namespaces/*.ts`(전 로케일) · `src/log-viewer/i18n.ts` · `public/_locales/*/messages.json`
   - 메시지 등록 3중: `src/background/messages.ts` · `BgRequest` union · `bgRequestTypes.ts`
   - `src/store/issues-store.ts` · `src/store/editor-store.ts`
   - 소스 스캔 그물의 목록: `store/__tests__/bundleBoundary.test.ts`(`ALLOWED`) · `builderLocaleWrap.test.ts`(WRAPPED/EXEMPT) · `scripts/coverage-report.mjs`(`BROWSER_BOUND_EXACT`)
   - 문서: `CLAUDE.md` · `docs/ARCHITECTURE.md` · `docs/DIRECTORY.md` · `docs/POSTMORTEM.md` · `coverage/baseline.json`
5. **`orch.md`를 dev에 로컬 커밋한 뒤 첫 워커를 띄운다** — 채팅 속 계획만으로 시작하지 않는다. 워크트리는 로컬 dev에서 갈라지므로, 커밋 안 된 계획은 워커가 못 읽는다. 브리프는 원본 계획과 `orch.md`를 함께 가리킨다. 이후 배치 분리·순서·소유권 변경, 리뷰/수정 라운드, 통합 커밋·검증 결과·미완 항목도 이 문서에 갱신한다.

## 1. 워커 띄우기

먼저 **`orca-cli` 스킬**을 읽고 Orca 워크트리·터미널로 배치를 관리한다. CLI 버전별 시작·재사용·완료·정리 절차는 그 스킬과 현재 `orca … --help`를 따른다.

- 구현 워커는 배치마다 **별도 워크트리**에서 띄운다. 워크트리엔 `node_modules`가 없으니 브리프 첫 단계가 `pnpm install --frozen-lockfile`이다.
- 세션의 권한 설정을 존중한다. 지휘자가 권한 우회 플래그를 임의로 추가하거나 다른 세션의 승인 창을 대신 누르지 않는다.
- **브리프는 파일로 쓰고 한 줄로 보낸다** — 여러 줄을 TUI에 붙이면 깨진다. 브리프에 반드시 넣는 것:
  - 계획 원본 경로와 담당 항목, **다른 배치 소유라 건드리지 말 것** 목록
  - `/ship bypass` 재정의: 워크트리 브랜치 = dev 등가 · **12단계(`/push`) 전에, 즉 11단계 커밋까지만** · `/push`·`/merge`·`/sync`·`/deploy`·`git push`·`/build` 금지
  - **`.env.local`이 필요하면 `cp .env.ci .env.local`만 허용** — 커밋된 더미 크레덴셜이다. 실 `.env.local`은 복사하지 않는다
  - 워커 게이트는 **`pnpm typecheck && pnpm test && pnpm sync:agents:check`** 이고 근거는 종료 코드뿐이다. ⚠️ **출력을 파이프(`| grep`·`| tail`)로 거르지 말라**고 적는다 — 파이프가 종료 코드를 삼켜 red가 green으로 보인다(malmoi 2026-09-30, 29건 red가 dev로 나갔다)
  - 빌드: `pnpm build`·`build:store`는 금지. `build:e2e`는 `/e2e-write` 안에서만 허용(`dist-e2e/`가 워크트리별로 격리된다)
  - 런타임 검증은 끝으로 미룬다 — 단 **(a) jsdom·node·e2e로 결정적으로 잴 수 있는 항목은 테스트로 먼저 쓰고**, 인계 문서의 "런타임 검증 목록"에는 **(b) e2e가 원리적으로 못 보는 축만** 남긴다(실 cross-origin CSS·실 sticky 사이트·실 광고 iframe·픽셀 판정·실 OAuth·실 외부 업로드 — 각 항목이 왜 (b)인지 한 줄)
  - 인계 프로토콜: `.scratch/handoff-<batch>.md`에 커밋 해시·게이트 결과(명령과 종료 코드)·「계획과 다른 점」·미완 항목을 기록하고 Orca 지침대로 완료를 한 번 알린 뒤 대기한다. 터미널 출력 마커는 완료 권한이 아니다.
- **런타임 검증 워커(코드 수정 없음)는 워크트리가 아니라 main 체크아웃에서 띄운다** — `/manual-smoke`·`/guide-shots`는 dist를 로드한 브라우저가 필요하고, dist는 main 체크아웃에 하나뿐이다.

## 2. 감시

- 완료·질문·차단 보고를 Orca로 받는다. heartbeat·빈 대기·타임아웃은 완료나 실패가 아니다 — 인계 문서와 실제 커밋을 대조한 뒤 다음 배치를 연결한다.
- 사용자가 결정해야 하는 질문은 전달하고(이미 받은 허가는 다시 묻지 않는다), 코드 수정은 소유 워커에게 돌려보낸다. 받은 보고는 처리 후 확인하고 미처리 배치를 누락하지 않는다.
- 사용자에게 질문했으면 답이 올 때까지 그 배치를 진행시키지 않는다.

## 3. 리뷰 → 수정 라운드

1. 인계 문서를 읽고, 그 배치 diff(`git log $(git merge-base dev <branch>)..<branch>`)를 **독립 리뷰 워커**(같은 패밀리, 리포트 전용 — `/code-review` 관점)에 맡긴다. 프롬프트에 계획 항목 · 인계 문서 주장 검증 · 변경 영역으로 grep한 `docs/POSTMORTEM.md` 항목 · 그 배치 특유의 위험(CLAUDE.md의 해당 불변식)을 넣는다.
   - **런타임 목록 분류도 판정시킨다** — (b)에 남긴 항목 중 jsdom·e2e로 결정적으로 잴 수 있는 것은 🟡("테스트로 옮겨라")다. 테스트가 중간 상태에서 멈추고 사용자가 보는 출력(렌더 결과·전송 payload)을 단언하지 않으면 그것도 🟡다.
2. 🔴·🟡 지적과 **사용자 결정이 필요한 항목**을 가른다. 결정은 현재 런타임의 질문 도구로 받는다.
3. 수정 라운드 브리프(`brief-<batch>-fix<N>.md`)를 소유 워커에게 보낸다. 모델·effort 조정과 재사용도 패밀리 경계를 지킨다.
4. 🔴 0이 될 때까지 반복한다. 워커가 스스로 계획과 다르게 간 곳(「계획과 다른 점」)은 리뷰가 반드시 판정한다.

## 4. 통합 (main 체크아웃 = dev)

```bash
git status --porcelain                              # 비어 있어야 한다
git cherry-pick $(git merge-base dev <branch>)..<branch>
pnpm typecheck && pnpm test && pnpm sync:agents:check   # 파이프 금지 — 종료 코드만 근거
```

그다음 **`/push`** 를 부른다(문서 신선도 트라이아지·미러 게이트·push·CI run URL 안내). `git push`를 직접 치지 않는다 — `/push`의 신선도 검사를 건너뛴다.

- 문서 신선도는 리뷰·`/push`가 찾은 드리프트를 **문서별 커밋**으로 얹는다(핫스팟 문서는 워커보다 지휘자가 통합 시점에 맞추는 게 충돌이 적다).
- 원본 계획의 항목 체크와 `orch.md`의 배치 상태·완료 증거를 갱신하는 커밋을 같이 얹는다.
- 겹침 때문에 기다리던 워커에게 "`<X>`가 dev에 들어갔다 — `git rebase dev` 후 계속"을 보낸다.
- CI(`verify` + `e2e-gate`)가 red면 그 배치 소유 워커에게 run URL과 실패 job을 보낸다. 지휘자가 고치지 않는다.
- ⚠️ **런타임 검증 워커가 main 체크아웃의 dist를 쓰는 동안에는 cherry-pick·`pnpm build`를 하지 않는다** — 로드된 확장과 소스가 어긋난 상태를 검증하게 된다. 검증 인계 뒤에 몰아서 통합한다.

## 5. 런타임 검증 (모든 배치가 dev에 들어간 뒤)

- 지휘자가 **`/build`를 한 번** 돌린다(사용자 지시로 간주 — `/orchestrate` 호출이 `/ship`처럼 그 범위를 포함한다). dist가 stale이면 검증이 헛돈다.
- **검증 워커를 main 체크아웃에서** 띄운다. 브라우저 하나에 확장 하나라 검증은 **직렬**이다.
- 범위는 각 인계 문서의 "런타임 검증 목록"(= (b)만)을 모은 것이다:
  - e2e가 못 보는 축 → `/manual-smoke`(시나리오 단일 출처 `e2e/MANUAL-SMOKE.md`)
  - 화면이 바뀐 배치 → `/guide-shots`
  - 레이아웃 → DESIGN.md 대비 ~400px 패널·다크모드·극단 데이터(긴 파일명·다국어) 점검
- **이슈 흐름**: 검증 워커가 결함을 **즉시** `gh issue create`로 낸다(제목에 `[<batch>]`·`[layout]` 태그). 지휘자는 새 이슈 번호를 모아(첫 건 뒤 몇 분 더) **그 화면·파일을 소유한 배치 워커**에게 "`#N` — rebase 후 `/tdd regression`으로 고쳐라"를 보낸다. 고친 뒤 재확인 검증이 이슈를 댓글과 함께 닫는다.
  - 커밋 메시지는 `Refs #N`이지 `Closes #N`이 아니다 — main 머지가 런타임 확인 전에 이슈를 닫지 않게 한다.
  - 회귀·버그를 고친 배치는 `/postmortem`까지 돈다(`/ship` 10.5단계).
- **권한**: 검증 워커가 막힌 작업을 지휘자가 대신 실행하는 권한 세탁은 금지한다. 권한 규칙을 넓혀야 하면 사용자 승인 후 범위를 좁혀서 한다.

## 6. 정리

- 지우기 전에 워크트리마다 확인한다: 추적 중인 미커밋 변경 0 · `git cherry dev <branch>`에 `+` 0(전부 dev에 들어감).
- 워크트리·브랜치 제거는 `orca-cli` 스킬의 절차를 따른다 — 먼저 소유 터미널을 정리한다.
- **인계 문서는 워크트리와 함께 사라진다** — 필요한 결론은 그 전에 정본 문서(`orch.md`·`docs/POSTMORTEM.md`)·커밋 메시지에 올라가 있어야 한다.
- **끝까지 기다리지 않는다 — GC처럼 수시로 치운다.** 위 두 검사를 통과하고 그 워커에게 보낼 지시가 더 없으면(소유 파일의 이슈가 남지 않았고, 대기 중인 수정 라운드가 없으면) 전체 검증이 끝나기 전이라도 지운다. 끝난 검증 터미널도 인계를 확인한 즉시 닫는다. 뒤에 결함이 올 것 같으면 **컨텍스트가 가장 여유 있는 워커 하나만** 남긴다 — 컨텍스트가 찬 워커(≈80%↑)부터 치운다. 치운 배치의 결함은 남은 워커나 새 워커에게 보낸다(브리프에 그 배치의 정본 문서를 가리킨다).

## 7. 리포트


## 금지 사항

- **`/merge`·`/deploy`·`/sync` 금지** — 프로덕션 앞의 사람 판단을 대신하지 않는다.
- **지휘자가 배치 코드를 직접 고치지 않는다** — 워커로 돌려보낸다.
- **워커의 `git push`·`/push`·`/build` 금지** — 원격 쓰기와 dist는 지휘자 소유다.
- **겹치는 파일을 가진 배치를 병렬로 띄우지 않는다.**
- **게이트 출력을 파이프로 거르지 않는다.**
- **검증 워커가 main 체크아웃의 dist를 쓰는 동안 cherry-pick·build 금지.**
- **다른 세션의 권한 프롬프트 승인·권한 규칙 확대를 사용자 승인 없이 하지 않는다.**
- 실 `.env.local`을 워커에게 복사시키지 않는다(`.env.ci`만).
