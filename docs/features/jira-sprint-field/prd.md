# Jira 제출 시 Sprint 선택

## 배경

Jira 제출 다이얼로그의 Jira 탭(`JiraIssueFields`)에는 이슈타입·담당자·우선순위·상위 에픽·연결 이슈·참조 6개가 있고, `jira-project-switch` 이후 프로젝트가 하나 더 붙는다. **스프린트는 없다.** 스크럼 팀은 버그를 등록한 뒤 Jira를 열어 백로그에서 해당 이슈를 찾아 스프린트로 끌어다 놓는 후속 작업을 손으로 한다.

이 기획이 다른 6개 필드와 다른 점은 **Sprint가 Jira의 표준 필드가 아니라는 것**이다. Jira Software가 설치될 때 만들어지는 커스텀 필드(`schema.custom === "com.pyxis.greenhopper.jira:gh-sprint"`)이고, 그래서 셋이 따라온다:

1. **필드 ID가 사이트마다 다르다.** `customfield_10020`이 흔하지만 보장이 없다 — 하드코딩 불가, 런타임 탐색이 필요하다.
2. **프로젝트마다 존재 여부가 다르다.** 칸반 보드만 있는 프로젝트, 보드가 없는 프로젝트, 에픽 이슈타입에는 스프린트가 없다. 없는데 값을 실으면 create가 400(`Field 'customfield_XXXXX' cannot be set. It is not on the appropriate screen`)으로 죽는다.
3. **값 목록이 REST API v3에 없다.** 스프린트 목록은 Jira Software(agile) API에만 있고(`/rest/agile/1.0/…`), 이건 **BugShot이 지금까지 한 번도 호출한 적 없는 API 계열**이다. OAuth scope 커버리지가 미검증이다.

1·2는 createmeta 상세 엔드포인트 한 번으로 동시에 해결된다(design §3). 3은 선행 spike로만 답이 나온다(Task 0).

**수요 근거의 강도**: 외부 리포트 없음. 저장소에서 이 수요의 사용자 신호는 0건이다. 근거는 "스크럼 팀이 등록 직후 Jira에서 하는 후속 조작을 제거한다"는 흐름 논거이며, 실측이 아니다. `docs/features/DROPPED.md`에 걸리는 항목은 없다(grep: sprint·agile·board — 전부 무관 문맥).

### 선행 기획 의존 (`jira-project-switch`)

이 문서는 **`jira-project-switch`가 구현된 코드 상태를 전제로 쓰였다.** 구체적으로 다음이 이미 있다고 가정한다:

- `EditorIssueFields.projectKey` — 제출 시점의 유효 프로젝트
- `src/sidepanel/tabs/jiraFields/project-change.ts`의 `applyProjectChange` — 프로젝트 전환 시 필드 정리 단일 출처
- `IssueTypeField`·`EpicField`·`RelatesField`가 `useJiraConfig()` 대신 prop `projectKey`를 받는 구조

선행 기획이 먼저 머지돼야 한다. 순서가 뒤집히면 이 문서의 §변경 범위 절반이 존재하지 않는 파일을 가리킨다.

## 목표

1. 제출 다이얼로그 Jira 탭에서 스프린트를 골라 그 스프린트에 이슈를 생성할 수 있다. **등록 후 Jira에서 백로그→스프린트 이동을 하지 않는다.**
2. **스프린트가 없는 조합에서는 필드 자체가 보이지 않는다.** 칸반 전용 프로젝트·보드 미연결 프로젝트·에픽 이슈타입에서 빈 콤보가 뜨지 않는다.
3. 고른 스프린트는 다음 제출에도 유지되되(sticky), **복원 시점에 아직 유효한 스프린트일 때만** 복원된다. 닫힌 스프린트로 제출되지 않는다.
4. 두 제출 진입점(신규 `IssueCreateModal`, 재제출 `DraftDetailDialog`)에서 동일하게 동작한다.
5. 스프린트를 고르지 않은 제출은 지금과 **바이트 단위로 같은** create payload를 만든다(회귀 0).

## 비목표 (Non-goals)

- **스프린트 생성·수정.** 목록에서 고르기만 한다.
- **닫힌(closed) 스프린트 선택.** `state=active,future`만 조회한다. 지난 스프린트에 사후 등록하는 흐름은 지원하지 않는다.
  - **다시 볼 조건**: "지난 스프린트에 넣어야 한다"는 사용자 신호가 실제로 관측되면. 필터 문자열 한 곳 변경이라 되돌리는 비용은 낮다.
- **스프린트 자동 선택.** active 스프린트가 하나뿐이어도 자동으로 박지 않는다 — 그러려면 다이얼로그를 열 때마다 board 목록 + 보드별 sprint 목록(N+1회)을 **선제로** 받아야 하는데, 스프린트를 안 쓰는 사용자에게도 매번 나간다. sticky(목표 3)가 반복 제출을 이미 커버한다.
- **에픽·스토리 계층에 따른 스프린트 필터링.** createmeta가 이슈타입별로 답을 주므로 별도 계층 규칙을 두지 않는다.
- **다른 Jira Software 필드(Story Points·Epic Link 등).** 같은 커스텀 필드 계열이지만 이번 스코프가 아니다. 이 기획이 만드는 `getSprintFieldMeta`는 Sprint 전용으로 두고 범용 "커스텀 필드 엔진"으로 일반화하지 않는다.
- **다른 7개 플랫폼의 대응 개념(Linear cycle·ClickUp sprint list 등).** 이번에 건드리지 않는다.
- **두 제출 핸들러의 중복 통합.** `IssueCreateModal`·`DraftDetailDialog`가 거의 같은 핸들러를 각자 들고 있고 이 변경이 복제를 한 겹 더 두껍게 만든다. `audit-refactor-6` 소관이며 이번에 착수하지 않는다.
- **보드 선택 UI.** 프로젝트에 보드가 여러 개면 스프린트를 합쳐 보여줄 뿐, 보드를 고르게 하지 않는다.

## 사용자 시나리오

### S1. 스프린트에 버그 등록 (핵심)

1. 스크럼 프로젝트 `WEB`으로 캡처 후 이슈 작성 → 제출 다이얼로그 Jira 탭.
2. 이슈타입이 `Bug`로 채워진 상태에서 **스프린트 행이 나타난다**(이슈타입 확정 후 판정이 끝나면서 삽입된다 — S5 참조).
3. 콤보를 열면 `WEB` 프로젝트에 걸린 모든 스크럼 보드의 active·future 스프린트가 한 목록에 뜬다. 보드가 여럿이면 각 항목 우측에 보드명이 흐리게 붙는다.
4. `Sprint 24`를 고르고 제출 → 이슈가 `Sprint 24`에 생성된다. Jira를 열어 옮기지 않는다.

### S2. 스프린트가 없는 프로젝트

1. 칸반 전용 프로젝트 `OPS`로 제출 다이얼로그를 연다.
2. **스프린트 행이 아예 없다.** 빈 콤보도, 비활성 컨트롤도, 안내 문구도 없다.
3. 나머지 필드는 지금과 동일하게 동작하고, 제출 payload는 스프린트 도입 전과 같다.

### S3. 다음 제출에서 유지 (sticky)

1. S1 직후 새 캡처 → 제출 다이얼로그.
2. 스프린트가 `Sprint 24`로 열린다(직전 **제출**값 — `lastSubmitFields.jira.sprintId`).
3. 그 사이 `Sprint 24`가 종료됐다면 **값이 조용히 비워진 채로 열린다.** 닫힌 스프린트로 제출되지 않는다.
4. 프로젝트를 바꾸면 스프린트도 비워진다(`applyProjectChange`).

### S4. 이슈타입 전환

1. 이슈타입을 `Bug` → `Epic`으로 바꾼다.
2. 에픽 create 화면에는 스프린트 필드가 없으므로 **행이 사라지고 고른 값도 비워진다.**
3. 다시 `Bug`로 되돌리면 행이 돌아오지만 값은 비어 있다(복구하지 않는다 — 전환 중 무효화된 값을 되살리는 규칙은 두지 않는다).

### S5. 판정 중 (로딩)

1. 다이얼로그를 열면 스프린트 행이 **처음부터 있지는 않다.** createmeta 응답이 오면 삽입된다(수백 ms).
2. 그동안 다른 필드는 정상 동작한다. 판정이 실패하면(네트워크 오류 등) 행은 나타나지 않는다 — **오류 표시도 하지 않는다.** 있는지 없는지 모르는 필드를 못 그렸다는 사실은 사용자에게 알릴 정보가 아니다.

### S6. 제출 실패

1. 스프린트를 고른 뒤 제출했는데 Jira가 400을 돌려준다(권한 변경·스프린트 종료 등 다이얼로그를 연 뒤 상태가 바뀐 경우).
2. 기존 제출 실패와 동일한 경로로 오류가 뜬다. **스프린트만 떼고 자동 재시도하지 않는다** — 사용자가 고른 값을 조용히 버리고 성공한 척하지 않는다.

## 성공 기준

- 스크럼 프로젝트에서 스프린트를 골라 제출하면 Jira 이슈의 Sprint 필드에 그 값이 들어간다(수동 확인 — 실계정).
- 칸반 프로젝트·보드 없는 프로젝트·에픽 이슈타입에서 스프린트 행이 렌더되지 않는다(e2e).
- 스프린트를 고르지 않은 제출의 `jira.submitIssue` payload가 도입 전과 동일하다(e2e — payload 스냅샷).
- 저장된 sticky 값이 닫힌 스프린트를 가리키면 다이얼로그가 빈 값으로 열린다(단위 테스트 — `resolveStickySprint`).
- 보드 2개에 걸친 중복 스프린트가 목록에 한 번만 나온다(단위 테스트 — `mergeBoardSprints`).
- `pnpm typecheck` + `pnpm test` 통과, `src/i18n/` 훅 자동 검사 green.
