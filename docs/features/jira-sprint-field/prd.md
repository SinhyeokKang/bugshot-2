# Jira 제출 시 Sprint 선택

## 배경

Jira 제출 다이얼로그의 Jira 탭(`JiraIssueFields`)에는 이슈타입·담당자·우선순위·상위 에픽·연결 이슈·참조 6개가 있고, `jira-project-switch` 이후 프로젝트가 하나 더 붙는다. **스프린트는 없다.** 스크럼 팀은 버그를 등록한 뒤 Jira를 열어 백로그에서 해당 이슈를 찾아 스프린트로 끌어다 놓는 후속 작업을 손으로 한다.

이 기획이 다른 6개 필드와 다른 점은 **Sprint가 Jira의 표준 필드가 아니라는 것**이다. Jira Software가 설치될 때 만들어지는 커스텀 필드(`schema.custom === "com.pyxis.greenhopper.jira:gh-sprint"`)이고, 그래서 셋이 따라온다:

1. **필드 ID가 사이트마다 다르다.** `customfield_10020`이 흔하지만 보장이 없다 — 하드코딩 불가, 런타임 탐색이 필요하다.
2. **프로젝트마다 존재 여부가 다르다.** 칸반 보드만 있는 프로젝트, 보드가 없는 프로젝트, 에픽 이슈타입에는 스프린트가 없다. 없는데 값을 실으면 create가 400(`Field 'customfield_XXXXX' cannot be set. It is not on the appropriate screen`)으로 죽는다.
3. **값 목록이 REST API v3에 없다.** 스프린트 목록은 Jira Software(agile) API에만 있고(`/rest/agile/1.0/…`), 이건 **BugShot이 지금까지 한 번도 호출한 적 없는 API 계열**이다. OAuth scope 커버리지가 미검증이다.

1·2는 createmeta 상세 엔드포인트 한 번으로 동시에 해결된다(design §3). 3은 선행 spike로만 답이 나온다(Task 0).

**수요 근거의 강도**: 외부 리포트 없음. 저장소에서 이 수요의 사용자 신호는 0건이다. 근거는 "스크럼 팀이 등록 직후 Jira에서 하는 후속 조작을 제거한다"는 흐름 논거이며, 실측이 아니다. `docs/features/DROPPED.md`에 걸리는 항목은 없다(grep: sprint·agile·board — 8항목 전부 캡처·CSS·picker 계열의 무관 문맥).

### 실효 사정거리 (이름값보다 좁다)

이 기능이 실제로 닿는 사용자는 **4중 교집합**이다:

1. Jira를 쓰고, **2.** 스프린트를 쓰는 보드를 운용하며(칸반 전용이면 필드 자체가 없다 — company-managed `scrum`과 team-managed `simple` 보드가 모두 해당하고, 후자도 스프린트를 반환하는 것이 실측됐다), **3.** 등록 시점에 스프린트를 정하는 사람(백로그에 쌓아두고 플래닝에서 일괄 배정하는 팀은 해당 없음), **4.** 그 프로젝트+이슈타입의 create 화면에 스프린트 필드가 올라가 있는 사이트.

여기에 **OAuth 연동 사용자는 재연동 전까지 제외**된다(아래 §OAuth scope 정책). 수요 신호 0건에서 출발하는 기획이므로 사정거리를 먼저 적어둔다 — Task 0의 비용 대비 판단이 여기에 걸린다.

### 선행 기획 의존 (`jira-project-switch`)

이 문서는 **`jira-project-switch`가 구현된 코드 상태를 전제로 쓰였다.** 구체적으로 다음이 이미 있다고 가정한다:

- `EditorIssueFields.projectKey` — 제출 시점의 유효 프로젝트. `JiraIssueFields`가 `fields.projectKey ?? accountProjectKey`로 해석해 하위 필드에 prop으로 내린다.
- `src/sidepanel/tabs/jiraFields/project-change.ts`의 **`resolveProjectChange`** — 프로젝트 전환 시 필드 정리 단일 출처(6키를 비우고 `priorityId`·`priorityName`·`cc`는 **보존**한다).
- `IssueTypeField`·`EpicField`·`RelatesField`가 prop `projectKey`를 받는 구조. `IssueTypeField`는 계정 기본 이슈타입을 **계정 기본 프로젝트일 때만** 주입한다(주입 경로가 둘 — effect + `effectiveValue`).
- `FieldCombobox`의 `ariaLabel?`·`testId?` prop(선행 기획이 추가). 이 기획은 **전달만** 한다.

선행 기획이 먼저 머지돼야 한다. 순서가 뒤집히면 이 문서의 §변경 범위 절반이 존재하지 않는 파일을 가리킨다.

### OAuth scope 정책 (발동 확정 — 2026-08-13 실측)

agile API는 classic scope로 덮이지 않는다(401 `scope does not match`). granular 3종을 `SCOPES`에 추가해야 하고, 그 조합은 **`read:board-scope:jira-software` + `read:project:jira` + `read:sprint:jira-software`** 다 — 가운데 것이 빠지면 나머지 둘이 있어도 여전히 401이다. classic 3종과의 혼용은 가능하다(동의 화면에 6종이 나란히 뜬다).

다만 `refreshOAuthToken`은 갱신 요청에 `scope`를 싣지 않고 access token의 scope는 **동의 시점에 고정**되므로, **기존 OAuth 사용자의 토큰은 새 scope를 얻지 못한다.**

정책은 **보수적**이다: 강제 재동의도, 연동 무효화도, 재연동 유도 UI도 만들지 않는다. 기존 사용자는 스스로 Jira를 다시 연동하는 시점에 이 기능을 얻고, 그 전까지는 스프린트 목록이 비어 보인다(오류 표시 없음 — design R6). API 토큰(Basic) 연동은 scope 개념이 없어 처음부터 정상 동작한다.

## 목표

1. 제출 다이얼로그 Jira 탭에서 스프린트를 골라 그 스프린트에 이슈를 생성할 수 있다. **등록 후 Jira에서 백로그→스프린트 이동을 하지 않는다.**
2. **create 화면에 스프린트 필드가 없는 조합에서는 행이 렌더되지 않는다.** 칸반 전용 프로젝트·보드 미연결 프로젝트·에픽 이슈타입에서 스프린트 행이 보이지 않는다. (행은 있는데 *목록*이 비는 경로는 별개로 존재한다 — S2b·design R6.)
3. 고른 스프린트는 다음 제출에도 유지되되(sticky), **복원 시점에 아직 유효한 스프린트일 때만** 복원된다. 닫힌 스프린트로 제출되지 않는다.
4. 두 제출 진입점(신규 `IssueCreateModal`, 재제출 `DraftDetailDialog`)에서 동일하게 동작한다.
5. 스프린트를 고르지 않은 제출은 지금과 **동일한 create payload**를 만든다(회귀 0). 단 존재 판정 요청 1회는 스프린트를 쓰지 않는 사용자에게도 추가된다(세션 캐시로 다이얼로그·이슈타입당 1회로 억제 — design §8).

## 비목표 (Non-goals)

- **스프린트 생성·수정.** 목록에서 고르기만 한다.
- **닫힌(closed) 스프린트 선택.** `state=active,future`만 조회한다. 지난 스프린트에 사후 등록하는 흐름은 지원하지 않는다.
  - **다시 볼 조건**: "지난 스프린트에 넣어야 한다"는 사용자 신호가 실제로 관측되면. 필터 문자열 한 곳 변경이라 되돌리는 비용은 낮다.
- **기존 OAuth 사용자의 강제 재동의·재연동 유도 UI.** §OAuth scope 정책 참조. 연동 상태를 무효화하거나 배너를 띄우지 않는다.
  - **다시 볼 조건**: 재연동 없이 못 쓰는 사용자 비중이 크다는 신호가 관측되면(§사후 검증의 `sprint_field_shown`이 그 대리 지표다). 그때 드는 비용은 연동 상태 진단 + 유도 UI + 재동의 후 상태 복구이며, 이 기획 크기를 넘는다.
- **스프린트 자동 선택.** active 스프린트가 하나뿐이어도 자동으로 박지 않는다 — 그러려면 다이얼로그를 열 때마다 board 목록 + 보드별 sprint 목록을 **선제로** 받아야 하는데, 스프린트를 안 쓰는 사용자에게도 매번 나간다. sticky(목표 3)가 반복 제출을 이미 커버한다.
  - **다시 볼 조건**: sticky가 없는 첫 제출의 이탈이 관측되면.
- **에픽·스토리 계층에 따른 스프린트 필터링.** createmeta가 이슈타입별로 답을 주므로 별도 계층 규칙을 두지 않는다.
- **다른 Jira Software 필드(Story Points·Epic Link 등).** 같은 커스텀 필드 계열이지만 이번 스코프가 아니다. 이 기획이 만드는 `getSprintFieldMeta`는 Sprint 전용으로 두고 범용 "커스텀 필드 엔진"으로 일반화하지 않는다.
  - **다시 볼 조건**: 같은 방식(createmeta로 존재 판정 + 별도 API로 값 조회)을 요구하는 필드가 **두 개 이상** 쌓이면. 하나뿐일 때 일반화하면 추상화가 사례 1개를 위해 존재하게 된다.
- **`FieldCombobox` 다중 그룹(보드별 heading) 지원.** design A5에서 기각했다. 공용 컴포넌트의 렌더 구조를 바꾸는 일이고, 보드 구분은 항목 내 보조 라벨로 충족된다.
- **다른 7개 플랫폼의 대응 개념(Linear cycle·ClickUp sprint list 등).** 이번에 건드리지 않는다.
- **두 제출 핸들러의 중복 통합.** `IssueCreateModal`·`DraftDetailDialog`가 거의 같은 핸들러를 각자 들고 있고 이 변경이 복제를 한 겹 더 두껍게 만든다. `audit-refactor-6` 소관이며 이번에 착수하지 않는다.
- **보드 선택 UI.** 프로젝트에 보드가 여러 개면 스프린트를 합쳐 보여줄 뿐, 보드를 고르게 하지 않는다.

## 사용자 시나리오

### S1. 스프린트에 버그 등록 (핵심)

1. 스크럼 프로젝트 `WEB`으로 캡처 후 이슈 작성 → 제출 다이얼로그 Jira 탭.
2. **이슈타입이 정해진 뒤에** 판정이 돈다. 계정 기본 프로젝트라 이슈타입이 `Bug`로 미리 채워져 있으면 다이얼로그를 여는 즉시, 프로젝트를 바꿔 이슈타입이 빈 상태면 이슈타입을 고른 뒤에 판정이 시작된다.
3. 판정 중에는 이슈타입 행 바로 아래에 로딩 표시가 자리를 잡고 있다가, 스프린트 필드가 있으면 그 자리가 콤보로 교체된다.
4. 콤보를 열면 `WEB` 프로젝트에 걸린 스크럼 보드(상위 5개)의 active·future 스프린트가 한 목록에 뜬다. 보드가 여럿이면 각 항목에 보드명이 둘째 줄로 붙는다.
5. `Sprint 24`를 고르고 제출 → 이슈가 `Sprint 24`에 생성된다. Jira를 열어 옮기지 않는다.

### S2. 스프린트가 없는 프로젝트

1. 칸반 전용 프로젝트 `OPS`로 제출 다이얼로그를 연다.
2. 판정이 끝나면 **로딩 표시가 사라지고 그 자리에 아무것도 남지 않는다.** 빈 콤보도, 비활성 컨트롤도, 안내 문구도 없다.
3. 나머지 필드는 지금과 동일하게 동작하고, 제출 payload는 스프린트 도입 전과 같다.

### S2b. 행은 있는데 목록이 비는 경우

create 화면에 스프린트 필드는 있지만 고를 스프린트가 없는 상태가 **정상적으로 존재한다**:

- 스크럼 보드는 있는데 active·future 스프린트가 0개(새로 만든 보드)
- 보드 조회가 실패한 경우 — 특히 **재연동 전 OAuth 사용자**(§OAuth scope 정책)
- 보드가 6개 이상이라 상위 5개 밖의 보드에만 스프린트가 있는 경우(design R6)

이때 콤보는 열리고 "일치하는 스프린트가 없습니다"만 보인다. **원인은 구분해 보여주지 않는다** — 세 경우를 가르려면 오류 표면을 따로 만들어야 하고, 그중 하나(재연동 전)는 사용자가 당장 할 수 있는 일이 없다. 대신 §사후 검증의 축으로 관측한다.

### S3. 다음 제출에서 유지 (sticky)

1. S1 직후 새 캡처 → 제출 다이얼로그.
2. 스프린트 칸은 **처음엔 비어 보인다.** 저장된 값(`lastSubmitFields.jira.sprintId`)이 아직 유효한지 확인한 뒤에만 이름이 채워진다 — "골라놨던 게 사라졌다"로 읽히지 않게 placeholder → 값 방향으로만 움직인다.
3. 그 사이 `Sprint 24`가 종료됐다면 값은 끝내 채워지지 않는다. 닫힌 스프린트로 제출되지 않는다.
4. 프로젝트를 바꾸면 스프린트도 비워진다(`resolveProjectChange`).

### S4. 이슈타입 전환

1. 이슈타입을 `Bug` → `Epic`으로 바꾼다.
2. 에픽 create 화면에는 스프린트 필드가 없으므로 **행이 사라지고 고른 값도 비워진다.**
3. 다시 `Bug`로 되돌리면 행이 돌아오지만 값은 비어 있다(복구하지 않는다 — 전환 중 무효화된 값을 되살리는 규칙은 두지 않는다). 판정 자체는 세션 캐시가 답해 재요청이 없다.

### S5. 판정 중 (로딩)

1. 다이얼로그를 열면 이슈타입 행 아래에 로딩 표시가 뜬다. 자리를 미리 잡으므로 **아래 필드들이 밀리지 않는다.**
2. 판정이 실패하면(네트워크 오류 등) 로딩이 사라지고 행은 나타나지 않는다 — **오류 표시는 하지 않는다.** 있는지 없는지 모르는 필드를 못 그렸다는 사실은 사용자에게 알릴 정보가 아니다.
3. 이슈타입이 아직 안 정해졌으면 판정 자체가 돌지 않는다(로딩도 뜨지 않는다).

### S6. 제출 실패

1. 스프린트를 고른 뒤 제출했는데 Jira가 400을 돌려준다(권한 변경·스프린트 종료 등 다이얼로그를 연 뒤 상태가 바뀐 경우).
2. 기존 제출 실패와 동일한 경로로 오류가 뜬다. **스프린트만 떼고 자동 재시도하지 않는다** — 사용자가 고른 값을 조용히 버리고 성공한 척하지 않는다.

### S7. 프로젝트 전환과의 합성

1. 프로젝트를 `WEB` → `API`로 바꾼다. `resolveProjectChange`가 이슈타입을 비우고 이슈타입 콤보가 자동으로 열린다(선행 기획 S1).
2. 이슈타입이 비었으므로 **스프린트 행이 사라진다.** 이슈타입을 고르면 새 프로젝트 기준으로 판정이 다시 돌아 행이 돌아오거나 안 돌아온다.
3. 좁은 사이드패널에서 이 구간에 행이 두 번 움직이는 것은 수용한다 — 로딩 자리 예약이 그 진폭을 이슈타입 행 아래 한 칸으로 묶는다.

## 사후 검증 (관측 축)

수요 신호 0건으로 출발하고, **무음 실패 모드가 4개**(봉투 키 오판 R3 / 필드 페이지 초과 R5 / 보드 조회 실패·상한 R6 / 제출 시점 재해석 실패 R7)인데 셋 다 증상이 *"필드가 안 보인다"·"스프린트가 조용히 빠졌다"*로 수렴한다. 사용자 신고 외의 진단 수단이 없으므로 관측 축을 함께 넣는다.

`issue_submitted` 이벤트에 **boolean 2축**:

- `sprint_field_shown` — 제출 시점에 스프린트 행이 렌더돼 있었나
- `sprint_selected` — payload에 `sprintId`가 실렸나

**한 축으로 합치지 않는다.** 합치면 "필드를 못 그렸다"(R3·R5·재연동 전 사용자)와 "필요 없어서 안 골랐다"가 구분되지 않아, 무음 버그가 "수요 없음"으로 오독된다.

스프린트 이름·id·보드명은 **보내지 않는다** — 클라이언트 온리 코어밸류와 충돌하지 않는다(`project_overridden`과 같은 논리). 구현 주의 2개: `analytics.ts`의 `ALLOWED_EVENTS.issue_submitted` 화이트리스트에 등록하지 않으면 `filterProperties`가 값을 무음 폐기하고, boolean은 `String()`으로 문자열화해야 통과한다(`replay_trimmed`·`project_overridden` 선례).

## 성공 기준

- 스크럼 프로젝트에서 스프린트를 골라 제출하면 Jira 이슈의 Sprint 필드에 그 값이 들어간다(수동 확인 — 실계정).
- 칸반 프로젝트·보드 없는 프로젝트·에픽 이슈타입에서 스프린트 행이 렌더되지 않는다(e2e).
- 스프린트를 고르지 않은 제출의 create 요청 body가 도입 전과 동일하다 — `fields` 키 집합이 정확히 4개(project·summary·description·issuetype)이고 createmeta 요청이 나가지 않는다(단위 테스트).
- **재제출 경로**(`DraftDetailDialog`)의 `jira.submitIssue` payload와 `lastSubmitFields.jira`에도 `sprintId`·`sprintName`이 실린다(목표 4 — UI는 `SubmitFieldsDialog`가 단일 마운트라 공유되고, 실제로 갈리는 건 상태·핸들러 2벌이다).
- 저장된 sticky 값이 닫힌 스프린트를 가리키면 다이얼로그가 빈 값으로 열린다(단위 테스트 — `resolveStickySprint`).
- 보드 2개에 걸친 중복 스프린트가 목록에 한 번만 나온다(단위 테스트 — `mergeBoardSprints`).
- `sprint_field_shown`·`sprint_selected`가 화이트리스트를 통과해 실제 payload에 실린다(단위 테스트 — 등록 누락 시 무음 폐기).
- `pnpm typecheck` + `pnpm test` 통과, `src/i18n/` 훅 자동 검사 green.
