# 프랑스어 UI 로케일 (fr)

## 배경

프랑스어권 충성 고객이 있다. 이건 시장 확대 베팅이 아니라 **이미 쓰고 있는 사용자에 대한 대응**이라, "어느 언어가 ROI가 높은가"는 이 기획의 질문이 아니다.

v1.7.19와 그 후속 커밋에서 로케일 축을 2-way 하드코딩에서 N-way로 바꾸는 인프라 작업을 끝냈다. 그 결과 **"어디를 채워야 하는지"는 이미 기계가 알려준다** — `LOCALES`에 코드를 하나 넣으면 컴파일러가 5곳을 지목하고, 대칭 테스트가 사전 세 벌의 누락·빈 값·placeholder 불일치를 잡는다. 그래서 이 기획이 정할 것은 배선이 아니라 **범위·품질·검증**이다.

`docs/features/DROPPED.md`에 로케일 관련 과거 판단은 없다(i18n·로케일·번역·다국어 키워드 grep 0건).

## 목표

- 설정 > 일반의 화면 언어 셀렉터에 `Français`가 나타나고, 선택하면 사이드패널 UI 전체가 프랑스어로 표시된다.
- `navigator.language`가 `fr*`인 신규 사용자는 첫 실행에서 프랑스어로 시작한다.
- 프랑스어 사용자의 `chrome://extensions`·웹스토어 카드에 확장 이름·설명이 프랑스어로 뜬다.
- 이슈에 첨부된 `logs.html`을 **브라우저 언어가 프랑스어인 사람이 열면** 프랑스어로 보인다(리포터의 설정이 아니라 읽는 사람 기준 — 기존 설계).
- AI 초안 작성 언어의 `자동`이 프랑스어 UI에서 `French`로 해석된다.
- 위 전부가 **기존 ko/en 동작을 한 바이트도 바꾸지 않는다.**

## 비목표 (Non-goals)

이번 스코프에서 명시적으로 제외한다. 전부 사용자 결정이다.

- **가이드 번역** — `guide/fr`을 만들지 않는다. 26페이지 16,318단어 + 스크린샷 73장이라 UI-only 결정을 뒤집는 규모다. `USER_GUIDE_URLS`가 폴백 허용 테이블이라 fr → en 가이드로 가는 게 이미 코드에 반영돼 있고, **UI에 별도 안내를 붙이지 않는다**(무표시 폴백).
- **`README.fr.md` · `docs/privacy.fr.md`** — 각각 3,468단어·5,599단어. privacy는 법적 문서라 번역 품질 부담이 다르고, 시행일 동기화 대상이 하나 더 늘어난다.
- **웹스토어 등록정보(CWS 대시보드)의 프랑스어 추가** — 스크린샷·상세 설명은 대시보드 수동 관리라 코드 밖이다. 이번엔 `public/_locales/fr/messages.json`이 커버하는 **확장 이름·짧은 설명·단축키 라벨 4키**까지만.
- **번역 품질에 대한 사람 검수** — 아래 "품질 정책" 참조. 이번엔 안 한다.
- **복수형(plural) 인프라** — 현재 `{n}m ago` 방식은 복수 규칙이 없다. 프랑스어는 영어와 같은 2-form이라 현 방식으로 덮인다. 러시아어(3-form)를 넣을 때 다시 볼 문제다.
- **폴백 허용 테이블의 fr 엔트리** — 프롬프트 스캐폴딩(`SECTION_DESC_BASE`·`MODE_HINTS`·`EXPECTED_SPLIT_HINT`·`SECTION_DESC`)은 "영어 뼈대 + `Write in X`"가 설계라 채우지 않는 게 정답이다. `MONTH_STYLE`도 en 폴백(`short`)이 `15 janv. 2026`으로 자연스러워 fr 엔트리가 불필요하다(`long`이면 `15 janvier 2026`).

## 품질 정책 — 사람 검수 없이 낸다

AI 초벌 번역을 검수 없이 출시한다. 충성 고객이 있으니 실사용 피드백이 첫 검수 루프가 된다는 판단이다.

이 결정은 **성공 기준을 바꾼다.** 번역 품질을 주장할 수 없으므로, 받아들일 수 있는 것은 **구조적 완결성**뿐이다:

- 키가 빠지지 않았다 · 빈 값이 없다 · placeholder 토큰이 어긋나지 않았다 → 기존 대칭 테스트가 이미 강제.
- **플랫폼 고유명사가 번역되지 않았다** → 신규 자동 가드. ko 사전이 이미 `Jira`·`GitHub`을 라틴 그대로 두는 선례가 있고(`integrations.ts`), AI가 가장 흔히 망치는 축이다.
- 레지스터(vouvoiement/tutoiement) 일관성·버튼 폭 넘침 → **자동으로 못 잡는다.** 수동 체크리스트에 남기되, 이번 릴리스의 차단 게이트가 아니다.

즉 이 기획의 완료 조건은 "프랑스어가 자연스럽다"가 아니라 **"프랑스어가 구조적으로 온전하고, 틀렸을 때 사용자가 알려줄 수 있는 상태로 나간다"**이다. 문서에 이걸 명시하는 이유는, 나중에 오역 리포트가 왔을 때 그게 회귀가 아니라 **예정된 경로**임을 분명히 하기 위해서다.

## 사용자 시나리오

**S1 — 프랑스어 브라우저 신규 설치**
1. `navigator.language`가 `fr-FR`인 사용자가 확장을 설치한다.
2. `detectLocale("fr-FR")` → `matchLocaleTag`가 `fr`을 최장 매칭으로 고른다.
3. 사이드패널이 프랑스어로 뜬다. `chrome://extensions`의 확장 이름·설명도 프랑스어.

**S2 — 기존 사용자가 수동 전환**
1. ko 또는 en으로 쓰던 사용자가 설정 > 일반 > 화면 언어를 연다.
2. 옵션이 `한국어 · English · Français` 세 개다(순서는 `LOCALES` 배열 순).
3. `Français` 선택 → 즉시 UI 전환, `chrome.storage.local`에 `fr` 영속.
4. background service worker도 `storage.onChanged`로 따라가, 이후 에러 토스트가 프랑스어로 온다.

**S3 — 가이드 폴백**
1. fr 사용자가 설정 하단 또는 이슈 탭의 가이드 버튼을 누른다.
2. `userGuideUrl("fr")` → `localeValue`가 en으로 폴백 → `bug-shot.com/en/docs`가 열린다.
3. **별도 안내 없이 영어 페이지**. 의도된 동작이다.

**S4 — AI 초안**
1. fr UI + AI 작성 언어 `자동`.
2. `resolveAiLanguage("auto", "fr")` → `localeAiPreset("fr")` → `"French"`.
3. 프롬프트 지시문에 `Write in French`가 실리고 초안이 프랑스어로 온다.
   프롬프트 뼈대(섹션 설명)는 영어로 남는다 — 설계다.

**S5 — logs.html을 다른 사람이 열기 (엣지)**
1. fr 사용자가 리포트를 제출해 `logs.html`이 이슈에 첨부된다.
2. 영어 브라우저 동료가 연다 → `detectLocale(navigator.language)` → `en` → **영어로 보인다.**
3. 리포터의 로케일이 박제되지 않는 게 의도다.

**S6 — 다운그레이드 (엣지)**
1. fr로 쓰던 사용자에게 fr이 없는 구버전이 롤백된다.
2. persist에 `"fr"`이 남아 있으나 `normalizeLocale`이 `DEFAULT_LOCALE`(en)로 교정한다.
3. 사전 조회가 `undefined`가 되어 `t()`가 죽는 일은 없다. **인프라에 이미 있는 방어**라 이번에 추가 작업이 없다.

## 성공 기준

- `pnpm typecheck` 0 에러 — 폴백 금지 5개 테이블이 전부 `fr`을 갖는다.
- `pnpm test` green — 사전 세 벌이 `BASE_LOCALE`(ko) 대비 키 대칭, 빈 값 0, placeholder 토큰 일치.
- 신규 가드 green — ko·en 양쪽에 등장하는 플랫폼 고유명사가 fr 값에도 그대로 있다.
- e2e green — 화면 언어 셀렉터가 옵션 3개를 `한국어 · English · Français` 순으로 렌더한다.
- ko/en 회귀 0 — 기존 스냅샷·프롬프트 출력 테스트가 전부 통과(특히 `draftRich.test.ts`·`buildAiDraftPrompt.test.ts`).
- 수동: fr로 전환했을 때 사이드패널 주요 화면에서 **버튼 텍스트가 넘치거나 잘리지 않는다**.
