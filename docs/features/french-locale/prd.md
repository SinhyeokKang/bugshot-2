# 프랑스어 UI 로케일 (fr)

## 배경

프랑스어권 충성 고객이 있다. 이건 시장 확대 베팅이 아니라 **이미 쓰고 있는 사용자에 대한 대응**이라, "어느 언어가 ROI가 높은가"는 이 기획의 질문이 아니다.

v1.7.19와 그 후속 커밋에서 로케일 축을 2-way 하드코딩에서 N-way로 바꾸는 인프라 작업을 끝냈다. 그 결과 **"어디를 채워야 하는지"는 이미 기계가 알려준다** — `LOCALES`에 코드를 하나 넣으면 컴파일러가 5곳을 지목하고, 대칭 테스트가 사전 세 벌의 누락·빈 값·placeholder 불일치를 잡는다. 그래서 이 기획이 정할 것은 배선이 아니라 **범위·품질·검증**이다.

`docs/features/DROPPED.md`에 **로케일 관련 판단은 없다**(i18n·로케일·번역·다국어 키워드 grep 0건). 다만 인접 비용 선례는 있다 — `DROPPED.md:15`가 "`IssuePreviewView`는 log-viewer가 재사용하므로 **복제 사전까지 파급된다**"를 기각 근거의 일부로 쓴다. 그게 정확히 이 기획이 치르는 비용(아래 사전 ②)이다.

## 목표

- 설정 > 일반의 화면 언어 셀렉터에 `Français`가 나타나고, 선택하면 사이드패널 UI 전체가 프랑스어로 표시된다.
- `navigator.language`가 `fr*`인 **신규** 사용자는 첫 실행에서 프랑스어로 시작한다.
- 프랑스어 사용자의 `chrome://extensions`·웹스토어 카드에 확장 이름·설명이 프랑스어로 뜬다.
- 이슈에 첨부된 `logs.html`을 **브라우저 언어가 프랑스어인 사람이 열면** 프랑스어로 보인다(리포터의 설정이 아니라 읽는 사람 기준 — 기존 설계).
- AI 초안 작성 언어의 `자동`이 프랑스어 UI에서 `French`로 해석된다 — **단, 직접 연결한 LLM(rich) 경로 한정.** Chrome 내장 AI(compact)는 `outputLanguage: "en"` 하드코딩이고 작성 언어 셀렉터 자체가 `promptStyle !== "rich"`로 숨겨져, 내장 AI 사용자는 fr UI에서도 초안이 영어로 온다.
- 위 전부가 **기존 ko/en 동작을 한 바이트도 바꾸지 않는다.**

## 비목표 (Non-goals)

이번 스코프에서 명시적으로 제외한다. 전부 사용자 결정이다.

- **가이드 번역** — `guide/fr`을 만들지 않는다. 26페이지 16,318단어(en 기준. ko는 12,832) + 스크린샷 74장이라 UI-only 결정을 뒤집는 규모다. `USER_GUIDE_URLS`가 폴백 허용 테이블이라 fr → en 가이드로 가는 게 이미 코드에 반영돼 있고, **UI에 별도 안내를 붙이지 않는다**(무표시 폴백).
  감수하는 결과는 두 가지다: ① `guide/AUTHORING.md:196`이 가이드 본문에 **로케일별 실제 화면 라벨 인용**을 의무화하므로, fr 사용자는 화면의 `Capturer l'élément`를 en 가이드에서 `Capture element`로 읽는다 ② `bug-shot.com/docs`의 글로벌 로케일 스위처에 fr 항목이 없어 그 페이지에서 언어를 바꿀 방법도 안 보인다.
  단, **기존 가이드 본문의 사실오류는 이번에 고친다** — `guide/{ko,en}/settings/general.md`가 지원 언어를 2개로 못 박고 "가이드도 언어에 맞춰 열립니다"라고 쓰고 있어 S3와 정면 모순이다(tasks.md Task 8).
- **`README.fr.md` · `docs/privacy.fr.md`** — 각각 3,468단어·5,599단어. privacy는 법적 문서라 번역 품질 부담이 다르고, 시행일 동기화 대상이 하나 더 늘어난다.
- **웹스토어 등록정보(CWS 대시보드)의 프랑스어 추가** — 스크린샷·상세 설명은 대시보드 수동 관리라 코드 밖이다. 이번엔 `public/_locales/fr/messages.json`이 커버하는 **확장 이름·짧은 설명·단축키 라벨 4키**까지만. 결과적으로 프랑스어 스토어 카드는 **프랑스어 이름·설명 + 영어 스크린샷·상세설명** 혼합이 된다. 의도한 상태다.
- **기존 사용자 인앱 공지** — 안 한다. `locale`은 v1부터 persist되는 필드이고 `detectLocale`은 **최초 시딩에만** 쓰이므로(`settings-ui-store.ts:211`), 이미 `ko`/`en`이 박힌 기존 사용자는 fr로 자동 전환되지 않는다. 배경이 지목한 그 고객도 설정 > 일반에서 직접 골라야 한다. 발견은 **CWS 릴리스 노트로 갈음**하고 인앱 배너·토스트를 만들지 않는다.
- **이슈 본문 로케일** — 별도 축이고 **`docs/features/issue-body-locale/`로 착지했다**(설정 > 이슈 > 이슈 본문 언어, `bodyLocale`). 이 기획에서는 안 건드린다. 그쪽이 상류에서 `src/i18n/namespaces/settings.ts`에 키를 넣고 뺐으므로 아래 위험 항목도 함께 볼 것.
- **compact(Chrome 내장 AI) 경로의 프랑스어 출력** — 위 목표 단서 참조. nano의 영어 few-shot과 `outputLanguage` 하드코딩을 손대는 건 별건이다.
- **번역 품질에 대한 사람 검수** — 아래 "품질 정책" 참조. 이번엔 안 한다.
- **복수형(plural) 인프라** — 현재 `{n}m ago` 방식은 복수 규칙이 없다. 프랑스어는 영어와 같은 2-form이라 현 방식으로 덮인다. 러시아어(3-form)를 넣을 때 다시 볼 문제다.
- **폴백 허용 테이블의 fr 엔트리** — 프롬프트 스캐폴딩(`SECTION_DESC_BASE`·`MODE_HINTS`·`EXPECTED_SPLIT_HINT`·`SECTION_DESC`)은 "영어 뼈대 + `Write in X`"가 설계라 채우지 않는 게 정답이다. `MONTH_STYLE`도 en 폴백(`short`)이 `15 janv. 2026`으로 자연스러워 fr 엔트리가 불필요하다(`long`이면 `15 janvier 2026`).
- **제품 지표 측정** — `locale`을 PostHog 속성으로 추가하지 않는다. `analytics.ts`의 `ALLOWED_EVENTS` 허용목록을 넓히면 privacy 검토가 따라오고, "fr 사용자가 전환했는지"는 이 규모의 대응에서 allowlist를 넓힐 만한 질문이 아니다. **즉 이 기능의 채택률은 측정하지 않는다.**

## 품질 정책 — 사람 검수 없이 낸다

AI 초벌 번역을 검수 없이 출시한다. 충성 고객이 있으니 실사용 피드백이 첫 검수 루프가 된다는 판단이다.

### 실패 반경 — 사이드패널에서 끝나지 않는다

`buildMarkdownIssueBody.ts`를 비롯한 8개 플랫폼 본문 빌더가 **제출 시점에 `t()`로 섹션 헤딩·환경 라벨·로그 요약 문장을 만든다.** 즉 fr 사용자가 제출하면 프랑스어 헤딩이 Jira·GitHub 이슈에 **영구 게시**된다. 사이드패널 흠집과 달리 되돌릴 수 없고, 동료가 읽는다.

이건 `logs.html`과 **반대 방향**이다 — S5는 읽는 사람 기준(리포터 로케일 미박제), 이슈 본문은 리포터 기준(박제됨). 두 표면의 정책이 다르다는 걸 알고 낸다. 이슈 본문 로케일을 UI와 분리하는 건 별도 축이라 비목표로 뺐다.

### 받아들일 수 있는 것은 구조적 완결성뿐

번역 품질을 주장할 수 없으므로:

- 키가 빠지지 않았다 · 빈 값이 없다 · placeholder 토큰이 어긋나지 않았다 → 기존 대칭 테스트가 이미 강제.
- **플랫폼 고유명사가 번역되지 않았다** → 신규 자동 가드. ko 사전이 이미 `Jira`·`GitHub`을 라틴 그대로 두는 선례가 있고(`integrations.ts`), AI가 가장 흔히 망치는 축이다.
- **manifest 문자열이 Chrome 길이 상한을 넘지 않았다** → 신규 자동 가드. 넘으면 확장이 로드되지 않거나 스토어 업로드가 거부된다.
- 레지스터(vouvoiement/tutoiement) 일관성·버튼 폭 넘침 → **자동으로 못 잡는다.** 수동 체크리스트에 남기되, 이번 릴리스의 차단 게이트가 아니다.

즉 이 기획의 완료 조건은 "프랑스어가 자연스럽다"가 아니라 **"프랑스어가 구조적으로 온전하고, 틀렸을 때 사용자가 알려줄 수 있는 상태로 나간다"**이다. 문서에 이걸 명시하는 이유는, 나중에 오역 리포트가 왔을 때 그게 회귀가 아니라 **예정된 경로**임을 분명히 하기 위해서다.

### 신고 채널 — 기존 문의 경로로 받는다

새 채널을 만들지 않는다. `SettingsFooter.tsx`의 **문의하기(`mailto:`)** 가 유일하고 충분한 경로다. fr 사용자에게도 프랑스어 라벨로 그 자리에 노출되므로, 오역을 발견한 사람이 도달할 수 있다. 다만 메일에 로케일 컨텍스트가 자동으로 실리지는 않는다 — 그건 감수한다.

### 철회 기준

fr을 `LOCALES`에서 빼는 건 다음 중 하나일 때다:

- 특정 화면에서 **의미가 반대로 뒤집힌** 오역이 보고된다(파괴적 동작을 안전한 것처럼 표기하는 부류).
- 오역 리포트가 **번역이 아니라 구조 문제**를 가리킨다(키 노출·placeholder 리터럴·문자 깨짐) — 이건 그물이 뚫린 것이라 회귀다.

그 외의 어색함·레지스터 불일치는 철회 사유가 아니라 **다음 패치에서 문자열만 고치는 대상**이다. fr 제거는 `LOCALES` 한 줄 되돌림 + `normalizeLocale`이 persist를 교정하므로(S6) 기술적으로 저렴하다.

## 사용자 시나리오

**S1 — 프랑스어 브라우저 신규 설치**
1. `navigator.language`가 `fr-FR`인 사용자가 확장을 설치한다.
2. `detectLocale("fr-FR")` → `matchLocaleTag`가 `fr`을 최장 매칭으로 고른다.
3. 사이드패널이 프랑스어로 뜬다. `chrome://extensions`의 확장 이름·설명도 프랑스어.

**S2 — 기존 사용자가 수동 전환**
1. ko 또는 en으로 쓰던 사용자가 설정 > 일반 > 화면 언어를 연다. (자동 전환은 없다 — 비목표 참조)
2. 옵션이 `한국어 · English · Français` 세 개다(순서는 `LOCALES` 배열 순 = 등록 순).
3. `Français` 선택 → 즉시 UI 전환, `chrome.storage.local`에 `fr` 영속.
4. background service worker도 `storage.onChanged`로 따라가, 이후 에러 토스트가 프랑스어로 온다.
5. 전환은 `set({ locale })` 1필드만 바꾼다 — **진행 중인 draft·캡처 상태는 초기화되지 않는다.**

**S3 — 가이드 폴백**
1. fr 사용자가 설정 하단 또는 이슈 탭의 가이드 버튼을 누른다.
2. `userGuideUrl("fr")` → `localeValue`가 en으로 폴백 → `bug-shot.com/en/docs`가 열린다.
3. **별도 안내 없이 영어 페이지**. 의도된 동작이고, 화면 라벨과 문서 라벨이 어긋난다(비목표 참조).

**S4 — AI 초안 (rich 경로)**
1. fr UI + 직접 연결한 LLM + AI 작성 언어 `자동`.
2. `resolveAiLanguage("auto", "fr")` → `localeAiPreset("fr")` → `"French"`.
3. 프롬프트 지시문에 `Write in French`가 실리고 초안이 프랑스어로 온다.
   프롬프트 뼈대(섹션 설명)는 영어로 남는다 — 설계다.
4. Chrome 내장 AI(compact)면 이 경로를 안 탄다 — 초안은 영어로 온다.

**S5 — logs.html을 다른 사람이 열기 (엣지)**
1. fr 사용자가 리포트를 제출해 `logs.html`이 이슈에 첨부된다.
2. 영어 브라우저 동료가 연다 → `detectLocale(navigator.language)` → `en` → **영어로 보인다.**
3. 리포터의 로케일이 박제되지 않는 게 의도다.

**S6 — 다운그레이드 (엣지)**
1. fr로 쓰던 사용자에게 fr이 없는 구버전이 롤백된다.
2. persist에 `"fr"`이 남아 있으나 `normalizeLocale`이 `DEFAULT_LOCALE`(en)로 교정한다.
3. 사전 조회가 `undefined`가 되어 `t()`가 죽는 일은 없다. **인프라에 이미 있는 방어**라 이번에 추가 작업이 없다.

**S7 — fr 사용자가 영어권 팀 트래커에 제출 (엣지)**
1. fr UI 사용자가 Jira/GitHub 이슈를 제출한다.
2. 기본값(`bodyLocale: "auto"`)이면 본문 섹션 헤딩이 **프랑스어로** 트래커에 올라간다(S5와 반대 방향).
3. 영어권 팀에 내보내야 하면 **설정 > 이슈 > 이슈 본문 언어를 `English`로 두면 된다** — `issue-body-locale` 기획이 이 축을 열었다. `LOCALES`에 `fr`이 등록되는 순간 그 셀렉터에도 `Français`가 자동으로 늘어나므로 이 기획 쪽 코드 수정은 0이다.
4. 남는 것은 **기본값이 프랑스어라는 사실 자체**다. 검수되지 않은 번역이 트래커로 나가는 게 싫으면 사용자가 명시적으로 골라야 하고, 그 선택지가 존재한다는 게 이전과의 차이다.

## 엣지 케이스

- **`fr-CA`·`fr-BE`·`fr-CH`** — `matchLocaleTag`가 prefix 최장 매칭이라 전부 `fr`로 떨어진다. 퀘벡 프랑스어 특유의 용어(`courriel` 등)를 따로 두지 않는다. 별도 로케일 코드로 갈라야 할 만큼의 요청이 오면 그때 본다.
- **브라우저 UI 언어 ≠ 인앱 로케일** — `chrome://extensions`·스토어 카드의 이름·설명은 **Chrome UI 언어** 축이라 인앱 셀렉터와 독립이다. 인앱을 fr로 바꿔도 브라우저가 en이면 확장 이름은 영어다. 반대도 마찬가지.
- **장기 브랜치 기간 중 상류의 i18n 키 추가** — git이 무음으로 자동머지하고 fr에만 키가 빠진 채 통과한다. parity 테스트가 머지 후에 잡는다(design.md "릴리스 전략").
- **`fr` 등록이 기존 e2e를 로컬에서만 깨뜨림** — 프랑스어 개발 머신에서 `navigator.language`가 fr로 잡히면, ko|en 교대 정규식을 쓰는 spec이 red가 된다. CI(en_US)는 통과하므로 발견이 늦다(tasks.md Task 6).
- **프랑스어 조판 문자** — `«　»` 안쪽과 `: ; ? !` 앞의 narrow no-break space(U+202F)는 Pretendard subset 밖이다. 번역에서 쓰지 않는다.

## 성공 기준

- `pnpm typecheck` 0 에러 — 폴백 금지 5개 테이블이 전부 `fr`을 갖는다.
