# 파일 첨부 실패 처리와 재첨부

## 배경

2026-10-01 기준 `dev`(`6274b9e6`, v1.7.45)에서 9개 제출 어댑터를 점검했다. 관련 기존 테스트 615개는 통과했지만 별도 실패 주입 17케이스에서 사용자 첨부 실패 무경고, Linear의 첨부 연결 실패 오판, Notion의 100블록 절단, 미해소 인라인 참조 잔존 등을 확인했다. 테스트 통과는 외부 서비스에서 실제 첨부가 성공한다는 뜻이 아니다.

- GitHub·GitLab·ClickUp은 실패한 `inline:` 참조를 본문에 남긴다.
- Jira·GitHub·GitLab·Linear·Asana·ClickUp·Slack은 사용자 파일 실패를 공통 경고 결과에 온전히 포함하지 않는다. Notion은 사용자 파일 실패를 `logsDropped`로 합친다.
- Linear는 업로드 이후 이슈 연결 실패를 삼킨다. Notion은 업로드 성공 후 페이지 블록을 잘라 파일 참조를 버릴 수 있다.
- 일반 트래커는 부분 실패에도 `markSubmitted`로 원본을 삭제한다. 토스트가 사라지면 누락 파일 확인·복구 경로가 없다.
- 공통 로딩 단계는 없는 Blob을 업로드 목록에서 제외한다. 어댑터의 성공 판정만 강화해서는 잡히지 않는다.

2026-09-29 회고(`docs/POSTMORTEM.md`)에서 `mediaDropped` 경고 토스트를 추가했지만 다음이 남았다. 이 기능은 그 잔여를 해소한다.

- 경고가 8초 토스트(`submitDroppedToast.ts`)뿐이라 놓치면 다시 볼 곳이 없다.
- 경고 축이 로그·미디어 둘뿐이라 사용자 파일·인라인 이미지 실패는 빠진다.
- 경고를 띄운 뒤에도 `markSubmitted`가 원본을 지워 누락 파일을 되살릴 수 없다.

관찰 사례: [GitHub #244](https://github.com/SinhyeokKang/bugshot-2/issues/244), [추가 관찰](https://github.com/SinhyeokKang/bugshot-2/issues/244#issuecomment-5921075838), [malmoi #166](https://github.com/SinhyeokKang/malmoi/issues/166). GitHub의 연속 실패 원인은 미확정이다. 이 기능의 완료를 그 원인 규명에 종속시키지 않는다.

## 단계 구성

두 단계로 나눠 출시한다. 1단계만으로 #244가 사용자에게 준 피해(무경고·본문 placeholder·원본 삭제)가 해소된다. 2단계는 1단계의 결과 계약과 보존 원본 위에 자동 재첨부를 얹는다.

| 단계 | 범위 |
|---|---|
| **1단계: 정직한 보고와 보존** | 파일별 결과 계약, 내부 마커·거짓 첨부 문구 제거, 지속 표시(완료 화면·목록 표시·복구 상세), 부분 실패 시 미완료 원본 보존·다운로드, 생성 체크포인트, 등록 여부 미확인 처리, 30일 보존 기한 |
| **2단계: 자동 재첨부** | 이슈 목록 **첨부 재시도**, 기존 이슈 본문 패치, 교차 인스턴스 배타, 브라우저 재시작 후 재개 |

## 목표

### 1단계

1. 사용자는 제출하기로 한 파일 각각이 이슈에 도달했는지(업로드되지 않음·이슈에 연결되지 않음·첨부됨 · 본문 링크 없음·업로드 결과 확인 안 됨)를 확인할 수 있다.
2. 이미 생성된 이슈의 식별자를 보존하고 첨부 실패를 전체 제출 실패로 표시하지 않는다. 같은 이슈를 다시 생성하는 버튼을 제공하지 않는다.
3. 지속되는 목록 표시와 복구 상세에서 누락 파일·복구 가능 여부·확인된 실패 사유를 보여주고, 미완료 파일은 다운로드할 수 있다. 완료 화면은 보조 표시이고 지속 상태의 단일 출처는 목록 표시와 복구 상세다.
4. 본문에 내부 `inline:`/ADF 마커 또는 사실과 다른 첨부 완료 문구를 보내지 않는다.
5. 보존된 복구 자료는 최대 30일 뒤 자동 삭제되고, 사용자가 언제든 직접 삭제할 수 있다.

### 2단계

6. 이슈 목록의 **첨부 재시도**를 누르면 실패한 파일과 미완료 단계만 다시 처리하고 기존 이슈의 첨부·본문을 갱신한다. 브라우저 재시작 후에도 이어 할 수 있다.

## 범위 결정

사용자 결정: **이슈 목록에서 트리거하는 자동 재첨부**를 구현하되 2단계로 분리한다. 클릭 한 번으로 실패 파일 업로드와 기존 이슈 본문 갱신을 수행한다. 예약·백그라운드 무한 재시도는 하지 않는다. 다운로드는 1단계의 기본 복구 경로이고, 2단계 이후에는 충돌·권한·원본 유실 등 자동 복구가 불가능할 때의 보조 경로다.

**원본 보존 방식**: 정상 제출을 위해 원본을 미리 복제하지 않는다. 부분 실패일 때 미완료 파일의 원본만 `markSubmitted`의 삭제와 `stripSubmitted`의 메타 비우기에서 제외해 그대로 남긴다. 제출 시점에 새로 만들어지는 바이트(logs.html, Asana JPEG 변환본, Notion ZIP)만 별도로 저장한다.

**보존 기한**: 보존된 복구 자료는 생성 시점부터 30일이 지나면 자동 삭제한다. 복구 상세에 남은 기간을 표시하고, 사용자는 **로컬 사본 삭제**로 언제든 지울 수 있다. 이 보존은 개인정보 보존 기간 변경이므로 `docs/privacy.{ko,en}.md`에 범위·기한을 명시한다.

**생성 전 실패**: 이슈가 아직 만들어지지 않은 실패는 현행대로 둔다. Linear·Notion처럼 생성 전 업로드가 실패하면 제출 전체가 실패하고 draft로 남는다. Slack 승격의 `requireMediaUpload` 가드도 유지한다. 부분 완료 복구는 **이슈 생성 이후**의 실패에만 적용한다.

실패 감지·보존 대상은 9개 어댑터의 신규 제출·저장 draft 제출·Slack 승격이다. 자동 재첨부(2단계)는 원격 갱신 API가 있는 Jira·GitHub·GitLab·Linear·Notion·Asana·ClickUp·Slack 8개에 적용한다. Custom Webhook은 임의 수신 서버에 기존 이슈 갱신 계약이 없어 부분 파일 재첨부를 제공하지 않는다. multipart는 기존 idempotencyKey를 사용하는 원래 요청의 재전송만 별도 구분하고, 이번에는 다운로드 복구를 유지한다. 캡처 이미지·영상·인라인 이미지·logs.html·사용자 파일을 모두 센다. 로그 OFF, 비활성 섹션의 인라인 이미지, Webhook JSON의 의도적 파일 미전송은 실패가 아니다.

## 비목표 (Non-goals)

- GitHub #244의 업로드 실패 원인 규명, 업로드 엔드포인트 교체, 예약 재시도·무한 백오프·자동 세션 재연결.
- 원격 파일 삭제·업로드 롤백·범용 전송 큐·사용자가 따로 올린 파일의 내용 기반 중복 탐지. 우리 시도의 locator와 단계 기록을 이용한 중복 방지는 포함한다.
- JPEG/WebP MIME 불일치 교정, Notion 장문 본문 전체 복원. Notion의 누락 첨부 블록 추가는 재첨부에 포함하되 잘린 일반 본문 전체를 복원하지 않는다.
- BugShot 서버 저장, 외부 파일 호스팅, 새 분석 이벤트, 새 권한·OAuth scope·env.
- 과거 제출에서 이미 삭제된 파일 복원. 옛 레코드에 첨부 성공을 소급 추정하지 않는다.
- 제출된 이슈의 일반 상세·편집 뷰. 새로 만드는 상세는 복구 대상 이슈의 읽기 전용 복구 화면에 한정한다.
- 첨부가 아닌 필드(제목·라벨·담당자 등)의 원격 재동기화.
- 재시도 진행률 알림·백그라운드 알림.
- Webhook 재전송 시 수신 서버의 중복 수신(기존 문제, 이번 범위 밖).

## 사용자 시나리오

### 1. 모든 첨부가 완료됨 (1단계)

1. 사용자가 기존 제출 버튼을 누른다.
2. 제출 대상 파일과 원본 존재를 확인한 뒤 전송한다. 원본은 복제하지 않는다.
3. 이슈와 첨부 연결이 완료되면 기존 성공 화면을 보여준다. 제출 시점 생성물 사본과 원본을 정리한다.
4. Slack의 원본 보존·승격 정책은 유지한다.

### 2. 이슈는 생성됐지만 일부 파일이 빠짐 (1단계 표시 · 2단계 재시도)

1. 완료 화면은 amber 경고 아이콘과 “이슈는 등록됐어요 · 첨부 N개 확인 필요”, 기존 이슈 링크를 표시한다. 스토어 리뷰 요청 버튼은 숨긴다.
2. 파일별로 `업로드되지 않음`, `이슈에 연결되지 않음`, `첨부됨 · 본문 링크 없음`, `업로드 결과 확인 안 됨`을 아이콘과 텍스트로 표시한다. HTTP 상태 등 근거가 있을 때만 용량·인증·권한·요청 제한으로 구체화한다.
3. 확인 버튼·패널 닫기는 보존 원본을 삭제하지 않는다. 이슈 목록 행의 메타 줄에 “첨부 확인 필요”가 남고, 행을 누르면 복구 상세가 열린다. 원격 이슈는 상세 안의 [이슈 열기]로 연다.
4. 1단계: 복구 상세에서 미완료 파일을 개별 다운로드한다. 다운로드 클릭을 원격 복구 완료로 간주하지 않는다. **로컬 사본 삭제**로 포기할 수 있다(원격 이슈는 그대로 남는다는 확인을 받는다).
5. 2단계: 행 또는 상세의 **첨부 재시도**를 누르면 실패 파일 업로드 → 기존 이슈 연결 → 본문 갱신을 자동으로 실행한다. 기존 이슈를 새로 만드는 호출은 하지 않는다. 업로드까지 성공한 파일은 연결/본문 단계만 재시도한다.
6. 2단계: 재시도 전체 성공이면 성공 토스트를 띄우고 표시와 보존 원본을 정리한다. 다시 일부만 실패하면 미완료 파일/단계와 마지막 사유를 남기고 “다시 N개 실패”를 알린다.

### 3. 제출 전에 원본 파일이 없거나 생성물 저장 실패 (1단계)

1. Blob 누락이나 제출 시점 생성물(logs.html 등)의 IndexedDB 저장 실패를 찾으면 외부 생성 요청 전에 중단한다.
2. 누락 파일 목록과 재선택·첨부 제거 후 재시도 안내를 표시한다. 기존 draft와 남은 파일은 유지한다.
3. 새 확인 다이얼로그로 “누락을 무시하고 제출”을 추가하지 않는다. 사용자가 기존 편집 화면에서 첨부 의도를 바꾼 뒤 제출한다.

### 4. 생성 후 통신 중단 또는 패널 재시작 (1단계)

1. 생성 응답에서 얻은 key/url/id를 첨부 작업 전에 체크포인트로 저장한다.
2. 이후 업로드 배치 실패는 기존 이슈와 보존 원본이 있는 부분 완료로 표시한다.
3. 생성 요청을 보냈지만 응답을 받지 못한 경우 “등록됐는지 확인할 수 없어요”로 구분한다. 자동 재전송하지 않는다. 새 제출과 재첨부를 모두 차단하고 다운로드만 제공한다.
4. 사용자가 목적지에서 확인한 뒤 복구 상세의 **등록되지 않았음 확인**을 누르면, AlertDialog가 “실제로 등록됐다면 같은 이슈가 두 번 만들어집니다”를 고지한다. 확인하면 레코드를 draft로 되돌려 다시 제출할 수 있다. 기존 이슈가 확인됐지만 locator가 없으면 다운로드로 복구한다.

### 5. 파일은 올라갔지만 본문 반영만 실패 (1단계 표시 · 2단계 재시도)

Jira·Asana·ClickUp의 네이티브 첨부 또는 Linear의 attachment 연결이 성공하고 본문 갱신만 실패하면 “첨부됨 · 본문 링크 없음”으로 표시한다. 2단계 재시도는 파일을 재업로드하지 않고 본문 갱신만 한다. 외부 본문에 마커가 남지 않게 최초 생성 본문도 안전한 폴백으로 만든다.

### 6. 원격 본문이 수정됨 (2단계)

재시도 시 원격 최신 본문을 조회해 우리 첨부 자리만 갱신한다. 다른 사람이 추가한 텍스트·상태·담당자·댓글은 보존한다. 해당 첨부 자리가 삭제·수정돼 안전한 치환이 불가능하면 본문 충돌을 알리고 자동 덮어쓰기를 중단한다. 업로드가 이미 끝났다면 다음 시도에서 다시 올리지 않는다.

### 7. 생성 전에 업로드가 실패함 (현행 유지)

Linear·Notion처럼 업로드가 생성보다 먼저인 플랫폼에서 업로드가 실패하거나, Slack 승격에서 `requireMediaUpload` 가드가 걸리면 이슈는 만들어지지 않는다. 기존처럼 제출 실패로 표시하고 draft로 남긴다. 부분 완료 표시나 복구 상세는 만들지 않는다.

### 8. 재시도할 수 없는 상태 (2단계)

재시도 전에 연결이 해제됐거나 다른 계정·workspace로 바뀌었으면 재시도 버튼 대신 연동 재연결 안내를 보여준다. 원격 이슈가 삭제됐거나(404) 권한을 잃었으면(403) 새로 만들지 않고 다운로드를 제공한다. Webhook 복구 항목은 재시도 버튼 없이 다운로드만 제공한다. 재시도 중에는 Slack 승격과 로컬 사본 삭제를 막는다.

### 9. 보존 기한 만료 (1단계)

복구 상세는 “N일 후 로컬 사본이 자동 삭제돼요”를 표시한다. 30일이 지나면 보존 원본과 생성물 사본을 지우고, 목록 표시는 “로컬 파일 없음” 상태로 남는다. 원격 이슈는 그대로다.

## 성공 기준

### 1단계

- 업로드 대상 각 파일에 최종 결과가 정확히 하나 있다. 응답에서 빠진 파일을 성공으로 처리하지 않는다.
- 원본 누락·생성물 저장 실패 시 원격 생성 호출 0회.
- 정상 제출에서 원본을 복제하지 않는다. 추가 저장은 제출 시점 생성물로 한정되고 완료 시 정리된다. 정상 제출의 UI는 기존과 같다.
- 생성 성공 후 첨부 예외가 나도 기존 이슈 key/url과 미완료 원본이 재시작 후 남는다.
- 실패한 사용자 PDF만 있는 제출도 부분 완료가 되며 logs.html 실패로 오표시하지 않는다.
- Linear 파일 업로드 성공 후 두 연결 경로가 모두 실패하면 파일을 복구 목록에 포함한다.
- Notion 100블록 절단으로 빠지는 파일을 성공으로 보고하지 않는다.
- 실패한 인라인 이미지가 제출 본문에 `inline:` 원문으로 남지 않는다.
- 성공·부분 완료·등록 여부 미확인의 세 상태가 화면과 저장소에서 구분된다. 부분 완료는 토스트가 아니라 지속 표시(목록·복구 상세)로 남는다.
- 등록 여부 미확인 상태에서는 새 제출과 재첨부가 모두 차단되고, **등록되지 않았음 확인** 후에만 새 생성이 가능하다.
- logs.html 사본은 제출 시점 바이트와 같고, 이후 로그가 늘어도 다운로드 내용은 바뀌지 않는다.
- 보존 자료는 30일 뒤 자동 삭제되고 로컬 사본 삭제로 즉시 지울 수 있다. `docs/privacy.{ko,en}.md`가 보존 범위·기한을 명시한다.
- Webhook 복구 항목은 다운로드만 노출된다.
- 생성 전 업로드 실패(Linear·Notion·Slack 승격 가드)는 기존과 같이 제출 실패 + draft 유지다.
- 전송 경로는 사용자 브라우저 → 선택한 플랫폼 그대로다. 실패 사유에 토큰·응답 본문·서명 URL을 저장하지 않는다.

### 2단계

- 재시도 전후 원격 이슈 ID가 같고 create 호출 수가 늘지 않는다. 두 패널의 동시 재시도는 하나만 진행된다.
- 업로드 성공/본문 실패 후 재시도에서 upload 호출 0회, 본문 갱신만 발생한다.
- 재시도 시 원격의 무관한 본문 수정은 유지되고 충돌한 첨부 자리는 덮어쓰지 않는다.
- 계정 변경·연결 해제·404·403에서 새 생성 없이 중단하고 대체 동작(재연결 안내·다운로드)을 보여준다.
- 재시도 결과(성공·다시 N개 실패)가 토스트와 live region으로 알려진다.

## 위험 요소

부분 실패 시 미완료 원본을 최대 30일 보존하므로 개인정보 보존 기간이 늘어난다. privacy 문서와 시행일을 함께 갱신한다. 제출 시점 생성물(특히 영상을 재임베드한 logs.html)은 정상 제출에도 잠시 저장되므로, 저장할 수 없으면 안전하게 제출을 중단한다. 응답을 잃은 원격 업로드는 중복 여부를 확정하지 못할 수 있다. locator로 재조회할 수 없으면 재업로드를 멈추고 확인/다운로드 경로를 제공한다. 생성 응답 유실 시 원격 중복 여부도 확정할 수 없으므로 보수적으로 재생성을 막는다. **등록되지 않았음 확인**은 사용자가 잘못 누르면 중복 이슈가 생길 수 있어 확인 다이얼로그로 위험을 고지한다.

과거 드랍 항목 `DROPPED.md`의 Notion `dataUrlToBlob` 통합과 GitHub 탭 wrapper 정리는 되살리지 않는다. 기존 파서와 MAIN world 주입의 구조를 유지한다.
