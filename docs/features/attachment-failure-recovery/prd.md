# 파일 첨부 실패 처리와 재첨부

## 배경

2026-10-01 기준 `dev`(`6274b9e6`, v1.7.45)에서 9개 제출 어댑터를 점검했다. 관련 기존 테스트 615개는 통과했지만 별도 실패 주입 17케이스에서 사용자 첨부 실패 무경고, Linear의 첨부 연결 실패 오판, Notion의 100블록 절단, 미해소 인라인 참조 잔존 등을 확인했다. 테스트 통과는 외부 서비스에서 실제 첨부가 성공한다는 뜻이 아니다.

- GitHub·GitLab·ClickUp은 실패한 `inline:` 참조를 본문에 남긴다.
- Jira·GitHub·GitLab·Linear·Asana·ClickUp·Slack은 사용자 파일 실패를 공통 경고 결과에 온전히 포함하지 않는다. Notion은 사용자 파일 실패를 `logsDropped`로 합친다.
- Linear는 업로드 이후 이슈 연결 실패를 삼킨다. Notion은 업로드 성공 후 페이지 블록을 잘라 파일 참조를 버릴 수 있다.
- 일반 트래커는 부분 실패에도 `markSubmitted`로 원본을 삭제한다. 토스트가 사라지면 누락 파일 확인·복구 경로가 없다.
- 공통 로딩 단계는 없는 Blob을 업로드 목록에서 제외한다. 어댑터의 성공 판정만 강화해서는 잡히지 않는다.

관찰 사례: [GitHub #244](https://github.com/SinhyeokKang/bugshot-2/issues/244), [추가 관찰](https://github.com/SinhyeokKang/bugshot-2/issues/244#issuecomment-5921075838), [malmoi #166](https://github.com/SinhyeokKang/malmoi/issues/166). GitHub의 연속 실패 원인은 미확정이다. 이 기능의 완료를 그 원인 규명에 종속시키지 않는다.

## 목표

1. 사용자가 보내기로 한 파일을 로딩 전부터 추적하고, 파일별 누락·업로드·이슈 연결·본문 반영 결과를 구분한다.
2. 이미 생성된 이슈의 식별자를 보존하고 첨부 실패를 전체 제출 실패로 표시하지 않는다. 같은 이슈를 다시 생성하는 버튼을 제공하지 않는다.
3. 이슈 목록의 **첨부 재시도**를 누르면 실패한 파일과 미완료 단계만 다시 처리하고 기존 이슈의 첨부·본문을 갱신한다. 브라우저 재시작 후에도 이어 할 수 있다.
4. 지속되는 결과 화면과 이슈 목록 상세에서 누락 파일·복구 가능 여부·확인된 실패 사유를 보여준다.
5. 본문에 내부 `inline:`/ADF 마커 또는 사실과 다른 첨부 완료 문구를 보내지 않는다.

## 범위 결정

사용자 결정: **이슈 목록에서 트리거하는 자동 재첨부**를 구현한다. 클릭 한 번으로 실패 파일 업로드와 기존 이슈 본문 갱신을 수행한다. 예약·백그라운드 무한 재시도는 하지 않는다. 다운로드는 충돌·권한·원본 유실 등 자동 복구가 불가능할 때의 보조 경로다.

실패 감지·보존 대상은 9개 어댑터의 신규 제출·저장 draft 제출·Slack 승격이다. 자동 재첨부는 원격 갱신 API가 있는 Jira·GitHub·GitLab·Linear·Notion·Asana·ClickUp·Slack 8개에 적용한다. Custom Webhook은 임의 수신 서버에 기존 이슈 갱신 계약이 없어 부분 파일 재첨부를 제공하지 않는다. multipart는 기존 idempotencyKey를 사용하는 원래 요청의 재전송만 별도 구분하고, 이번에는 다운로드 복구를 유지한다. 캡처 이미지·영상·인라인 이미지·logs.html·사용자 파일을 모두 센다. 로그 OFF, 비활성 섹션의 인라인 이미지, Webhook JSON의 의도적 파일 미전송은 실패가 아니다.

## 비목표 (Non-goals)

- GitHub #244의 업로드 실패 원인 규명, 업로드 엔드포인트 교체, 예약 재시도·무한 백오프·자동 세션 재연결.
- 원격 파일 삭제·업로드 롤백·범용 전송 큐·사용자가 따로 올린 파일의 내용 기반 중복 탐지. 우리 시도의 locator와 단계 기록을 이용한 중복 방지는 포함한다.
- JPEG/WebP MIME 불일치 교정, Notion 장문 본문 전체 복원. Notion의 누락 첨부 블록 추가는 재첨부에 포함하되 잘린 일반 본문 전체를 복원하지 않는다.
- BugShot 서버 저장, 외부 파일 호스팅, 새 분석 이벤트, 새 권한·OAuth scope·env.
- 과거 제출에서 이미 삭제된 파일 복원. 옛 레코드에 첨부 성공을 소급 추정하지 않는다.

## 사용자 시나리오

### 1. 모든 첨부가 완료됨

1. 사용자가 기존 제출 버튼을 누른다.
2. 제출 대상 파일을 확인하고 임시 복구 사본의 로컬 저장을 마친 뒤 전송한다.
3. 이슈와 첨부 연결이 완료되면 기존 성공 화면을 보여준다. 임시 사본을 정리한다.
4. Slack의 원본 보존·승격 정책은 유지한다.

### 2. 이슈는 생성됐지만 일부 파일이 빠짐

1. 완료 화면은 “이슈가 등록됐지만 일부 첨부를 확인해야 합니다”와 기존 이슈 링크를 표시한다.
2. 파일별로 `첨부 실패`, `연결 실패`, `본문 반영 실패`, `결과 확인 불가`를 표시한다. HTTP 상태 등 근거가 있을 때만 용량·인증·권한·요청 제한으로 구체화한다.
3. 사용자는 이슈 목록에서 **첨부 재시도**를 누른다. 실패 파일 업로드 → 기존 이슈 연결 → 본문 갱신을 자동으로 실행한다. 기존 이슈를 새로 만드는 호출은 하지 않는다. 업로드까지 성공한 파일은 연결/본문 단계만 재시도한다.
4. 확인 버튼·패널 닫기는 복구 사본을 삭제하지 않는다. 이슈 목록에 “첨부 확인 필요” 표시와 상세 진입점이 남는다.
5. 재시도 전체 성공이면 배지와 복구 사본을 정리한다. 다시 일부만 실패하면 미완료 파일/단계와 마지막 사유를 남긴다. 사용자의 **복구 자료 삭제**로 포기할 수도 있다. 다운로드 클릭을 원격 복구 완료로 간주하지 않는다.

### 3. 제출 전에 원본 파일이 없거나 복구 사본 저장 실패

1. Blob 누락·IndexedDB quota/트랜잭션 실패를 찾으면 외부 생성 요청 전에 중단한다.
2. 누락 파일 목록과 재선택·첨부 제거 후 재시도 안내를 표시한다. 기존 draft와 남은 파일은 유지한다.
3. 새 확인 다이얼로그로 “누락을 무시하고 제출”을 추가하지 않는다. 사용자가 기존 편집 화면에서 첨부 의도를 바꾼 뒤 제출한다.

### 4. 생성 후 통신 중단 또는 패널 재시작

1. 생성 응답에서 얻은 key/url/id를 첨부 작업 전에 체크포인트로 저장한다.
2. 이후 업로드 배치 실패는 기존 이슈와 복구 사본이 있는 부분 완료로 표시한다.
3. 생성 요청을 보냈지만 응답을 받지 못한 경우 “등록 여부 확인 필요”로 구분한다. 자동 재전송하지 않는다.
4. 생성 여부가 미확인이고 원격 식별자가 없다면 자동 재첨부를 시작하지 않는다. 사용자가 목적지에서 확인 후 “등록되지 않았음 확인”을 명시적으로 선택해야 새 생성을 허용한다. 기존 이슈가 확인됐지만 locator가 없으면 이번 범위에서는 다운로드 복구한다.

### 5. 파일은 올라갔지만 본문 반영만 실패

Jira·Asana·ClickUp의 네이티브 첨부 또는 Linear의 attachment 연결이 성공하고 본문 갱신만 실패하면 “첨부됨 · 본문 반영 실패”로 표시한다. 재시도는 파일을 재업로드하지 않고 본문 갱신만 한다. 외부 본문에 마커가 남지 않게 최초 생성 본문도 안전한 폴백으로 만든다.

### 6. 원격 본문이 수정됨

재시도 시 원격 최신 본문을 조회해 우리 첨부 자리만 갱신한다. 다른 사람이 추가한 텍스트·상태·담당자·댓글은 보존한다. 해당 첨부 자리가 삭제·수정돼 안전한 치환이 불가능하면 본문 충돌을 알리고 자동 덮어쓰기를 중단한다. 업로드가 이미 끝났다면 다음 시도에서 다시 올리지 않는다.

## 성공 기준

- 업로드 대상 각 파일에 최종 결과가 정확히 하나 있다. 응답에서 빠진 파일을 성공으로 처리하지 않는다.
- 원본 누락·복구 저장 실패 시 원격 생성 호출 0회.
- 생성 성공 후 첨부 예외가 나도 기존 이슈 key/url과 복구 파일이 재시작 후 남는다.
- 실패한 사용자 PDF만 있는 제출도 부분 완료가 되며 logs.html 실패로 오표시하지 않는다.
- Linear 파일 업로드 성공 후 두 연결 경로가 모두 실패하면 파일을 복구 목록에 포함한다.
- Notion 100블록 절단으로 빠지는 파일을 성공으로 보고하지 않는다.
- 실패한 인라인 이미지가 제출 본문에 `inline:` 원문으로 남지 않는다.
- 성공·부분 완료·등록 여부 미확인의 세 상태가 화면과 저장소에서 구분된다.
- 실패 파일의 Blob 바이트가 제출 직전 사본과 같고, 기존 로그가 늘어도 다운로드 내용은 바뀌지 않는다.
- 재시도 전후 원격 이슈 ID가 같고 create 호출 수가 늘지 않는다. 두 패널의 동시 재시도는 하나만 진행된다.
- 업로드 성공/본문 실패 후 재시도에서 upload 호출 0회, 본문 갱신만 발생한다.
- 재시도 시 원격의 무관한 본문 수정은 유지되고 충돌한 첨부 자리는 덮어쓰지 않는다.
- 전송 경로는 사용자 브라우저 → 선택한 플랫폼 그대로다. 실패 사유에 토큰·응답 본문·서명 URL을 저장하지 않는다.

## 위험 요소

복구 사본을 사전에 저장하므로 일시적으로 저장량이 늘고 제출 준비 시간이 길어진다. 저장할 수 없으면 안전하게 제출을 중단한다. 응답을 잃은 원격 업로드는 중복 여부를 확정하지 못할 수 있다. locator로 재조회할 수 없으면 재업로드를 멈추고 확인/다운로드 경로를 제공한다. 생성 응답 유실 시 원격 중복 여부도 확정할 수 없으므로 보수적으로 재생성을 막는다.

과거 드랍 항목 `DROPPED.md`의 Notion `dataUrlToBlob` 통합과 GitHub 탭 wrapper 정리는 되살리지 않는다. 기존 파서와 MAIN world 주입의 구조를 유지한다.

## 추가 관찰

[GitHub #245](https://github.com/SinhyeokKang/bugshot-2/issues/245)는 새 ego-browser task space와 example.com 탭에서 영역 이미지·logs.html 모두 성공했다. #244와 페이지·로그량·task space가 함께 달라졌으므로 특정 원인이나 해결책으로 단정하지 않는다. 이 성공 사례는 재첨부 기능의 필요성과 독립적이다.
