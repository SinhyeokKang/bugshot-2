# Jira 프로젝트 제출 시 전환

## 배경

**8개 플랫폼 중 Jira만 제출 시점에 최상위 스코프를 고를 수 없다.** 제출 다이얼로그(`SubmitFieldsDialog`)의 각 플랫폼 탭을 나열하면 비대칭이 한눈에 보인다:

| 플랫폼 | 제출 시 고르는 최상위 스코프 | 컴포넌트 |
|---|---|---|
| GitHub | 레포(owner/repo) | `RepoCombobox` |
| Linear | 팀 (+ 프로젝트 별도 필드) | `TeamCombobox` |
| Notion | 데이터베이스 | `DatabaseCombobox` |
| GitLab | 프로젝트 | `ProjectCombobox` |
| Asana | 워크스페이스 → 프로젝트 | `WorkspaceCombobox` + `ProjectCombobox` |
| ClickUp | 워크스페이스 → 스페이스 → 리스트 | `WorkspaceCombobox` 외 2 |
| Slack | 채널 | `ChannelCombobox` |
| **Jira** | **없음** | — |

Jira 탭(`JiraIssueFields`)에 있는 건 이슈타입·담당자·우선순위·상위 에픽·연결 이슈·참조 6개뿐이고, 프로젝트는 `accounts.jira.projectKey`(연동 탭 설정)를 그대로 읽어 제출한다(`IssueCreateModal.tsx:174`, `DraftDetailDialog.tsx:426`). 프로젝트가 다른 이슈를 올리려면 **연동 탭으로 이동 → 프로젝트 변경 → 다시 제출 흐름으로 복귀**해야 하고, 그 변경은 전역 기본값을 덮어써 다음 제출에도 남는다.

이 상태가 코드에 명시적으로 기록돼 있다 — `initialJiraFields.ts` 주석: *"Jira는 project가 이슈 필드가 아니라 Connect 계정 설정(account.projectKey)이고 그게 진실이다."*

### "정합"이 정확히 무엇을 맞추는가 (재분류의 정당화)

위 표만으로는 논거가 절반이다. sticky 축으로 다시 보면 8개 플랫폼이 **두 계보**로 갈린다:

- **제출 목적지 계보** (GitHub repo·Linear team·Notion DB·GitLab project·Slack channel): 직전 제출값이 우선, 연동 기본값은 fallback.
- **거친 스코프 계보** (Asana workspace·ClickUp workspace): sticky 없이 **연동 기본값 우선**(`AsanaIssueFields.tsx:23-24`, `ClickupIssueFields.tsx:29-30`).

즉 기존 `initialJiraFields` 주석이 Jira project를 Asana workspace와 같은 위상으로 본 것은 **그 자체로 일관된 설계였다.** 이 기획은 "빠진 걸 채운다"가 아니라 **project를 workspace 위상에서 repo/team 위상으로 재분류**하는 것이다.

재분류의 근거는 Jira 데이터 모델이다. Jira project는 **이슈가 실제로 들어가 사는 컨테이너**이고 이슈 키(`WEB-123`)의 접두사이며 이슈타입·에픽·권한의 스코프다 — GitHub repo·Linear team과 같은 층이다. 반면 Asana/ClickUp workspace는 그 위의 **조직 경계**이고 실제 목적지는 그 아래 project/list다(그래서 저 둘은 workspace 밑에 별도 목적지 콤보를 또 갖는다). 이 층위 차이가 재분류를 정당화한다. `POSTMORTEM 2026-06-30`이 정한 규칙 — *"제출 목적지 필드는 last 우선, defaults는 fallback. Asana/ClickUp의 defaults 우선은 workspace(거친 스코프) 한정 예외"* — 과 정확히 같은 판정이다.

**잔여 비대칭은 남는다**: 이 변경 후에도 Asana·ClickUp 2개는 defaults 우선으로 남는다. 위 근거대로 그건 예외가 아니라 다른 층위이므로 정합 목표에 어긋나지 않는다.

### 이 기획의 출처와, 원 목표와의 거리 (명시해둔다)

출발점은 "Jira 워크스페이스(사이트)를 여러 개 쓰는 사용자가 재연동 없이 제출하게 하기"였다. 조사 결과 사이트 복수화는 다음을 요구한다:

- `JiraAccount`에 사이트 배열 + 사이트별 프로젝트·이슈타입·담당자 (평면 필드를 전부 사이트 스코프로 이동, 마이그레이션 필요)
- 연동 다이얼로그의 다중 선택 + 사이트별 온보딩
- `lastSubmitFields.jira`의 사이트별 키잉, 연동 해제의 2단 분리(사이트/전체)

반면 **프로젝트 전환은 background 변경이 0이다** — `jira.listIssueTypes`·`jira.searchEpics`·`jira.submitIssue`가 이미 `projectKey`를 인자로 받고, 사이트가 안 바뀌므로 `loadAuth()`의 단일 슬롯 전제도 그대로다.

따라서 **이번 스코프는 원 목표를 완전히 달성하지 않는다.** 한 사이트 안에서만 움직이며, 사이트를 오가려면 여전히 연동 해제 → 재연결이 필요하다. 정당화는 둘이다: (1) 실사용에서 "사이트 여러 개"보다 "프로젝트 여러 개"가 흔하고, (2) 위 재분류 논거대로 플랫폼 간 정책 정합이 그 자체로 목적이다.

**(1)은 출처 없는 단언이다** — 위 "수요 근거의 강도"와 같은 층의 추정이며 실측이 아니다. (2)만이 관측 가능한 사실 위에 서 있다. 원 요청이 실제로 "사이트 여러 개"였다면 이 릴리스는 요청자 기준으로 부분 해결에 그친다.

**수요 근거의 강도**: 외부 리포트는 없다. 저장소에서 이 수요의 사용자 신호는 0건이다. 근거는 플랫폼 간 비대칭(위 표 — 관측 가능한 사실)과 사용 흐름 이탈(연동 탭 왕복)이며, 실측이 아니다. `DROPPED.md`에 걸리는 항목은 없다.

## 목표

1. 제출 다이얼로그 Jira 탭에서 프로젝트를 바꿔 그 프로젝트로 제출할 수 있다. **연동 탭으로 이동하지 않는다.**
2. 고른 프로젝트가 유지된다(sticky). **연동 탭의 기본 프로젝트(`accounts.jira.projectKey`)는 바뀌지 않는다.** 유지는 두 층으로 나뉜다:
   - **세션 안**: `EditorIssueFields.projectKey`가 세션 스냅샷(`EDITOR_SNAPSHOT_KEYS`) 대상이므로, 고르기만 하고 제출 없이 닫아도 그 편집 세션에는 남는다.
   - **세션 너머**: 다음 제출 다이얼로그가 `lastSubmitFields.jira.projectKey`로 열린다 — 이쪽은 **제출에 성공한 값**만 기록된다.
3. 프로젝트를 바꾸면 그 프로젝트에서 무효인 하위 필드가 자동으로 비워져, 다른 프로젝트의 이슈타입 ID·담당자·에픽으로 제출이 시도되지 않는다.
4. 두 제출 진입점(신규 이슈 `IssueCreateModal`, 저장 이슈 재제출 `DraftDetailDialog`)에서 동일하게 동작한다.

## 비목표 (Non-goals)

- **복수 Jira 사이트(워크스페이스) 동시 사용.** 사이트 전환 UX는 만들지 않는다 — 지금처럼 연동 해제 → 재연결로 남는다. (사이트 식별자 `siteId`는 stale 복원 차단 판별자로만 기록한다. 사이트 *축*이 데이터에 들어오지만 사이트 *전환*은 지원하지 않는다는 뜻이다.)
  - **다시 볼 조건**: 한 사용자가 두 Jira 사이트를 오간다는 신호가 실제로 관측되면. 그때 드는 비용은 design A4에 열거돼 있다 — `JiraAccount` 사이트 배열 재구성 + 마이그레이션, 연동 UI 다중 선택 + 사이트별 온보딩, `lastSubmitFields.jira`의 사이트별 키잉, 연동 해제 2단 분리, background `loadAuth()` 단일 슬롯 전제 해체. 프로젝트 전환은 그중 어느 것도 요구하지 않아 먼저 뗐다.
- **연동 직후 프로젝트 강제 설정 완화.** `SetupDialog`가 `projectKey` 없으면 모달로 열리고 취소 시 `removeAccount("jira")`하는 현재 흐름을 유지한다. 기본값이 있어야 다이얼로그가 무언가로 열린다.
- **API 토큰(`kind: "apiKey"`) 인증의 복수 사이트.** `baseUrl`+토큰이 사이트에 묶여 있어 성립하지 않는다. 프로젝트 전환 자체는 apiKey/OAuth 양쪽에서 동일하게 동작한다.
- **다른 7개 플랫폼의 스코프 UI 변경.** 이미 있다.
- **8개 스코프 콤보의 공통 컴포넌트화.** `ProjectField`는 같은 골격(콤보 + 디바운스 검색 + fallbackLabel)의 8번째 구현이 되지만, 이번에 추출하지 않는다. 위 "UI 변경 없음"이 막는 건 동작 변경뿐이라 이 항목을 따로 못박는다.
- **두 제출 핸들러의 중복 통합.** `IssueCreateModal`·`DraftDetailDialog`가 거의 같은 374줄 핸들러를 각자 들고 있고 이번 변경이 그 복제를 한 겹 더 두껍게 만든다. 이건 **`audit-refactor-6` 소관(🟡43)이며 이번에 착수하지 않는다.** 구현 중 "이참에 같이"가 나오면 스코프가 3배가 된다.
- **연동 탭 `ProjectCombobox` 변경.** 기본 프로젝트 설정 컨트롤로 그대로 둔다(클라이언트 필터라 51번째 프로젝트를 못 찾는 한계도 그대로 — S4 참조).
- **프로젝트 전환 시 값 소멸에 대한 확인·경고 UI.** 8개 플랫폼 전부 무음 리셋이라 Jira에만 붙이면 그 순간 비일관이 된다. S1-3 참조.
- **`markSubmitted`의 `issueTypeName` 정확도 개선.** 지금 계정 기본값을 저장해 실제 고른 이슈타입과 어긋날 수 있다(기존 부정확성). 아래 "위험 요소" 참조 — 이번에 고치지 않는다.

## 사용자 시나리오

### S1. 다른 프로젝트로 한 번 제출 (핵심)

1. 연동 탭 기본 프로젝트는 `WEB`. 캡처 후 이슈 작성 → 제출 다이얼로그 Jira 탭.
2. 최상단 **프로젝트** 행이 `WEB`로 열려 있다. 콤보를 열어 `API`를 고른다.
3. 이슈타입·담당자·상위 에픽·연결 이슈가 비워진다. **우선순위와 참조(cc)는 남는다** — 둘 다 사이트 전역 스코프다(design §4).
4. 이슈타입이 비었으므로 제출 버튼이 잠기고, **이슈타입 콤보가 자동으로 열려** 다음에 할 일이 바로 보인다.
5. 이슈타입을 고르고 제출 → `API` 프로젝트에 등록된다.
6. **연동 탭을 열어보면 기본 프로젝트는 여전히 `WEB`이다.**

3단계의 값 소멸은 **확인 없이 일어난다.** 이는 Jira만의 결정이 아니라 8개 플랫폼 공통 동작이다 — 다른 어느 플랫폼도 최상위 스코프를 바꿀 때 토스트·확인 다이얼로그를 띄우지 않는다. 여기에만 확인을 붙이면 그 순간 비일관이 되므로 선례를 따른다(비목표 참조).

### S2. 다음 제출에서 유지 (sticky)

1. S1 직후 새 캡처 → 제출 다이얼로그.
2. 프로젝트가 `API`로 열린다(직전 **제출**값). 담당자·우선순위 등 S1에서 쓴 값도 복원된다.
3. 프로젝트를 `WEB`으로 되돌리면 하위 필드가 다시 비워진다.

이 복원은 `confirmDraft`의 `restorable` 게이트(세션에서 이미 담당자·우선순위를 고른 상태면 직전 제출값을 덮지 않는다) **바깥**에서 일어난다 — 게이트 조건은 프로젝트와 무관하므로 `projectKey`만 예외로 항상 복원한다(design §2).

### S3. 저장 이슈 재제출

1. 이슈 목록 → 저장된 초안 상세(`DraftDetailDialog`) → 제출.
2. S1과 동일하게 프로젝트 행이 있고, 바꿔서 제출할 수 있다.

### S4. 프로젝트가 많은 조직

1. 콤보를 열면 서버가 최대 50개를 준다(`/rest/api/3/project/search?maxResults=50`).
2. 검색어를 입력하면 서버 검색(`query` 파라미터)으로 좁혀진다 — 51번째 프로젝트도 찾을 수 있다.

**연동 탭 `ProjectCombobox`는 이 개선을 받지 않는다.** 그쪽은 `query` 없이 1회 호출 후 클라이언트 필터라 51번째 프로젝트에 도달하지 못한다. 같은 제품 안에서 프로젝트 검색 동작이 둘로 갈리는 셈이지만, 연동 탭 변경은 비목표다.

### S5. 다른 사이트의 직전 제출값 (latent 엣지)

1. 사이트 A에서 프로젝트 `WEB`으로 제출한 이력이 있다.
2. 연동을 해제하고 사이트 B로 재연결한다.
3. 다른 사이트의 직전 제출값이 남아 있다면, 제출 다이얼로그는 그 값을 복원하지 않고 **현재 계정의 기본 프로젝트로 연다.**

**현재 UI에서 2단계는 도달 불가능하다.** 연결 버튼이 `disabled={connected}`(`JiraConnectForm.tsx:190`)라 재연동은 반드시 `removeAccount`를 거치고, `removeAccount`가 `lastSubmitFields.jira`를 함께 지운다. 토큰 갱신도 `cloudId`를 바꾸지 않는다. 그럼에도 `siteId` 게이트를 두는 이유는 `finalize()`가 `removeAccount` 없이 `setAccount("jira", next)`로 계정을 통째 교체하는 코드 경로가 실재하고(`JiraConnectForm.tsx:163`, apiKey는 `:328`), prop 하나가 유일한 방어이기 때문이다. 값싼 판별자로 latent를 닫아둔다(design §1).

**이 게이트가 막지 못하는 경로가 하나 있다** — 편집 세션이 살아 있는 채로 해제→재연결하면 세션 `issueFields.projectKey`가 그대로 남는다. design R7 참조(이번 비목표).

### S6. 프로젝트 목록 조회 실패 (엣지)

1. 권한·네트워크 문제로 목록을 못 불러오면 **콤보를 열었을 때** 리스트 자리에 에러 문구가 뜬다. 닫힌 트리거에는 별도 표시가 없다.
2. 트리거에는 선택된 프로젝트 **키**가 유지된다(`fallbackLabel`). 프로젝트 이름은 목록 로드에 성공해야 보이므로, 실패 시에는 키만 보인다.
3. 제출 자체는 현재 선택값으로 계속 가능하다(목록은 선택을 바꿀 때만 필요).

### S7. 연동 탭에서 기본 프로젝트를 바꾼 뒤 (자주 발생)

1. 직전 제출은 `API`였다. 연동 탭에서 기본 프로젝트를 `WEB` → `DESIGN`으로 바꾼다.
2. 다음 제출 다이얼로그는 **`DESIGN`이 아니라 `API`로 열린다** — 직전 제출값이 기본값을 이긴다.
3. 편집 중인 이슈가 이미 있었다면 그 세션은 원래 프로젝트를 계속 유지한다.

**의도된 동작이다**(설정은 기본값, 직전 제출이 우선 — 위 "정합" 논거의 제출 목적지 계보 규칙). 다만 사용자에게는 "설정을 바꿨는데 반영이 안 된다"로 보일 수 있고, Jira는 다른 플랫폼과 달리 `defaults` 객체가 아니라 평면 계정 필드라 "설정 = 진실"로 읽히는 구조다. **이번 스코프에서는 UI 단서를 추가하지 않는다**(i18n 신규 키 0 유지). design R1·R4로 추적한다.

## 성공 기준

- 연동 탭을 거치지 않고 제출 다이얼로그 안에서만 프로젝트를 바꿔 제출이 성공한다(S1).
- 제출 후 `accounts.jira.projectKey`가 불변임을 스토어에서 확인할 수 있다(S1-6).
- 프로젝트 전환 시 `issueTypeId`·`assigneeId`·`parentKey`·`relates`가 비고 `priorityId`·`cc`가 남는 것이 단위 테스트로 고정된다.
- 다른 프로젝트에 존재하지 않는 계정 기본 이슈타입 ID가 **값으로도 표시로도** 자동 주입되지 않는다(`IssueTypeField`의 `defaultId` 자동 적용 경로 2곳 — 위험 요소 R2).
- 두 진입점(`IssueCreateModal`·`DraftDetailDialog`)에서 동일 동작이 e2e로 판정된다.
- `pnpm typecheck` + `pnpm test` 통과.

### 사후 검증 (채택)

수요 신호 0건으로 출발하는 기획이므로 **쓰이는지 관측할 수단을 함께 넣는다.** `issue_submitted` 이벤트에 `project_overridden`(boolean — 제출한 프로젝트가 계정 기본값과 다른가) 한 축을 추가한다. 프로젝트 키 자체는 사용자 데이터라 보내지 않으므로 클라이언트 온리 코어밸류와 충돌하지 않는다.

**되돌림 판단 기준**: 릴리스 후에도 `project_overridden`이 사실상 0에 수렴하면, 이 기능은 비대칭 해소라는 명분만 남고 실사용 가치는 없다는 뜻이다. 그 경우 UI 행을 되돌리는 것을 검토한다(데이터 모델 변경은 무해하므로 남겨도 된다).
