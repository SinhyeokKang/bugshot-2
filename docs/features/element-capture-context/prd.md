# Element 캡처 컨텍스트 확장

## 배경

element mode는 요소 스타일을 편집하고 before/after 스냅샷을 이슈에 담는다. 두 스냅샷 모두 **요소 bbox + 24px 마진**으로만 크롭된다(마진의 단일 출처는 `src/sidepanel/capture.ts:11`. 요소 rect 측정은 `src/content/picker.ts`의 `viewportRectOf`이고 여기서는 마진을 붙이지 않는다). 이 고정 규칙에서 두 가지 문제가 나온다.

**1. 맥락 소실.** 다이얼로그 안 버튼 하나를 수정하면 그 버튼만 찍힌다. 리포트를 받는 사람은 이 이미지가 어느 화면·어느 다이얼로그의 것인지 알 수 없다. 모달만의 문제가 아니다 — 테이블 셀을 고치면 어느 행인지, 리스트 아이템 안 요소를 고치면 어느 항목인지 식별할 수 없다. 특히 테이블 행 식별이 안 되는 리포트는 사실상 재현 불가다.

**2. `display:none` 캡처 깨짐.** 요소를 제거하는 수정에서 `getBoundingClientRect()`가 전부 0을 반환한다. rect가 `{0,0,0,0}`이 되어 크롭이 `(-24,-24,48,48)`로 계산되고, `clampCropRect`(`src/sidepanel/lib/crop-rect.ts`)가 이를 `(0,0,24,24)`로 가둔다. 결과적으로 **after 이미지가 페이지 좌상단 24×24 픽셀 조각**이 된다. `visibility:hidden`·`opacity:0`은 rect가 살아있어 빈 사각형이라도 나오지만, `display:none`은 완전히 무의미한 이미지가 나온다.

두 문제는 **같은 지점**(캡처 rect를 요소 자신의 bbox로만 잡는 결정)에서 나오지만 **해결 메커니즘은 다르다.**

- 문제 1(맥락 소실) → 요소를 감싸는 의미 단위 컨테이너로의 **확장**
- 문제 2(`display:none`) → 요소 rect가 0×0일 때 before 시점 rect를 재사용하는 **0×0 폴백**

확장이 걸리면 조상은 `display:none`이 아니므로 rect가 정상이라 문제 2도 더불어 해소된다. 다만 아래 P1대로 폴백이 다수 경로인 설계이므로, **문제 2의 주된 해결책은 0×0 폴백이다.**

## 설계 원칙 (이 기능의 판단 기준)

이 기능은 **버그 리포트의 증거물을 만드는 경로**를 건드린다. 잘못된 이미지가 담긴 리포트는 없는 것보다 나쁘다 — 받는 사람이 엉뚱한 곳을 보고 재현을 시도하기 때문이다. 그래서 아래 원칙이 편의성·커버리지보다 우선한다. **각 원칙은 개별 판단이 아니라 이 우선순위에서 파생된 결과다.**

### P1. 불확실하면 확장하지 않는다

확장 여부가 조금이라도 의심스러우면 현행 방식(요소 bbox + 24px)으로 폴백한다. "아마 이 컨테이너일 것"이라는 추정으로 확장하지 않는다. **커버리지 손실은 의도적으로 수용한 비용이다** — 확장이 안 걸리는 요소가 많아지는 것은 실패가 아니라 설계대로 동작하는 것이다.

**정확도와 기능 체감이 충돌하면 정확도가 이긴다.** 확장이 자주 안 걸려서 기능이 밋밋해 보이는 것은 감수한다. 발동률이 낮다는 관찰은 게이트를 푸는 근거가 되지 않는다.

이 원칙이 iframe 내부 요소와 `StyleChangesDialog` 재캡처 경로를 확장 대상에서 제외한 근거이기도 하다(비목표 참조).

### P2. before 판정의 폴백은 현행 동작이므로 회귀 위험이 없다

**이 원칙은 before 판정 단계에 적용된다.** before 캡처의 모든 실패 경로(신호 없음·게이트 미달·selector 생성 실패·rect 무효)가 **같은 출구**로 수렴한다. 확장이 실패하면 지금과 완전히 동일한 이미지가 나온다. 이 구조 덕분에 before 게이트를 아무리 조여도 기존 동작이 나빠지지 않는다. 반대로 게이트를 풀면 **새로운 실패 모드가 생긴다** — 비대칭적이므로 조이는 쪽이 항상 안전하다.

**after 재검증 실패는 이 보장 밖이다.** before가 확장에 성공한 뒤 after가 폴백하면 출구는 "현행 동작"이 아니라 프레이밍이 다른 두 이미지, 즉 현행에 없던 상태다. 그래도 각 이미지는 개별적으로 유효하므로(잘못된 영역을 찍은 게 아니다) 허용하되, 그 전에 저장된 before rect로 대체를 한 번 시도한다. 목표·비목표에 이 비대칭을 명시한다.

### P3. 신호는 구조적으로 확정된 것만 쓴다

`<tr>`이 테이블 행이라는 것, `[role="dialog"]`가 다이얼로그라는 것은 **오탐이 불가능한 사실**이다. 반면 "배경색이 있으니 카드일 것", "면적이 튀니 경계일 것", "`position:absolute`니 팝오버일 것"은 추정이다. 후자는 임계값 튜닝이 끝없고, 틀렸을 때 엉뚱한 영역이 찍혀 P1을 정면으로 위반한다. 커버리지를 늘리려고 추정 신호를 넣지 않는다.

### P4. 판정은 예측 가능해야 한다

같은 페이지에서 같은 요소를 **같은 화면 상태로** 고르면 항상 같은 결과가 나와야 한다. 판정 결과가 연속적으로 흔들리면 사용자는 왜 어떤 때는 되고 어떤 때는 안 되는지 알 수 없고 재현도 못 한다.

G1(뷰포트 완전 포함)은 그 자체로 화면 상태에 의존하는 판정이다 — 절반만 보이는 `<tr>`은 폴백되고, 다 보이게 스크롤한 뒤 고르면 확장된다. 클램프 방식 대비 개선된 것은 **판정이 연속값에서 이진값으로 바뀌었다**는 점이다. 클램프는 스크롤 픽셀마다 캡처 면적이 미묘하게 달라져 "왜 이 크기인지" 설명할 수 없지만, G1은 "화면에 다 보이면 컨테이너, 아니면 요소"라는 사용자가 눈으로 확인할 수 있는 규칙이다. 그리고 **어느 쪽이든 잘린 이미지는 나오지 않는다.**

### P5. 부분적 맥락보다 확실한 요소가 낫다

컨테이너가 화면에 다 안 들어와 잘린 이미지를 만드느니, 요소만 정확히 찍는 편이 낫다. 잘린 컨테이너는 맥락을 반만 주면서 이미지 크기 비용은 다 치른다. **"컨테이너 전체를 보여줄 수 있을 때만 컨테이너를 보여준다."**

### P6. 캡처 범위 확대는 프라이버시 확대다

BugShot의 코어 밸류는 클라이언트 온리 프라이버시다(`CLAUDE.md`). 캡처 범위를 넓히면 선택 요소 주변의 고객 데이터가 이미지에 더 들어간다. 후보를 강한 시맨틱으로 제한하고 인접 개인정보를 넓게 포함하는 컨테이너(`form`·landmark)를 제외한 것은 이 이유이기도 하다.

**캡처 이미지가 나가는 경로는 제출만이 아니다.** AI 초안을 실행하면 before/after 이미지가 **제출 전에** 사용자가 선택한 LLM endpoint로 먼저 전송된다(`src/sidepanel/lib/prompts/draftStyleElements.ts`). 확장은 그 경로에 실리는 픽셀도 함께 늘린다. 두 경로 모두 BugShot 서버를 거치지 않는다는 구조는 그대로지만, 사용자가 범위를 확인할 수단은 AI 실행 이전에도 접근 가능해야 한다.

검토 수단의 현실은 다음과 같다. 약 400px 사이드패널의 before/after 표에서 이미지 실효 폭은 **약 105px**이고(`src/sidepanel/components/StyleChangesTable.tsx`의 `table-fixed` 39% 컬럼), 320px 패널이면 약 78px까지 줄며 **확대·다운로드 경로가 없다**. 즉 이 표는 "무엇이 찍혔는지 대략 확인"까지는 되지만 세부 판독은 안 된다. 이번 스코프에서는 UI를 추가하지 않고, 수동 테스트로 확장 이미지의 개인정보 노출 면적을 육안 검증한다. 확대·다운로드 경로 추가는 별도 과제로 남긴다.

## 목표

- 요소를 감싸는 **의미 단위 컨테이너**를 신뢰할 수 있는 신호로 식별해, 확신이 있을 때만 캡처 rect를 그 경계로 확장한다.
- 확장 조건에 하나라도 미달하면 **현행 방식(요소 bbox + 24px)으로 폴백**한다. 리포트 정확도를 해칠 수 있는 경로를 만들지 않는다.
- `display:none` 등으로 요소 rect가 0이 되어도 의미 있는 after 이미지를 남긴다.
- before/after가 **가능한 한 같은 컨테이너**를 기준으로 찍힌다. after 재검증이 실패하면 저장된 before rect로 대체를 시도하고, 그것도 신뢰할 수 없으면 요소 bbox로 폴백한다(비대칭 허용 — P2).
- 자동 확장으로 선택 요소 주변의 고객 데이터가 더 포함될 수 있음을 제품 trade-off로 다룬다. 후보를 강한 시맨틱으로 제한하고, 확장 범위를 수동 검증한다.

## 비목표 (Non-goals)

- **하이라이트 오버레이를 그리지 않는다.** 편집한 요소를 이미지에 사각형으로 표시하는 기능은 이번 스코프에서 제외한다. 대신 면적 게이트로 과확장 자체를 막아 요소가 점처럼 작아지는 상황을 만들지 않는다.
- **캡처 범위 조절 UI를 추가하지 않는다.** 사용자가 확장 범위를 넓히거나 좁히는 컨트롤은 만들지 않는다. 자동 판정이 틀리면 폴백으로 수렴하므로 복구 수단이 따로 필요하지 않다(P2).
- **확장 적용 여부를 UI에 표시하지 않는다.** 폴백이 곧 현행 동작이고 범위 조절 수단도 없으므로, 상태를 노출해도 사용자가 취할 액션이 없다. 판단 부담만 늘린다(P2).
- **before/after 이미지 크기 대칭을 보장하지 않는다.** 리플로우로 컨테이너 크기가 변하거나 after가 폴백하면 두 이미지의 크기·프레이밍이 달라질 수 있다. 크기를 맞추려면 좌표 고정 + 강제 스크롤 복원이 필요한데 그 비용이 이득보다 크다(design.md 대안 검토 1).
- **시각 휴리스틱을 쓰지 않는다.** 배경색·border·box-shadow·border-radius·면적 점프 비율은 추정 신호라 채택하지 않는다(P3).
- **positioned 휴리스틱을 쓰지 않는다.** `position:absolute|fixed` + `z-index`만으로는 의미 단위를 보장할 수 없다(P3). 시맨틱 없는 커스텀 팝오버·백드롭은 폴백한다.
- **시맨틱이 없는 컨테이너를 추론하지 않는다.** `<div class="card">` 같은 커스텀 패널은 확장 대상이 아니며 폴백된다(P3). 알려진 한계로 수용한다.
- **폼·광범위 landmark를 자동 확장하지 않는다.** `form`·`section`·`nav`·`aside`·`header`·`footer`·`[role="group"]`는 인접 개인정보를 넓게 포함하거나 의미 경계가 모호하다(P6).
- **뷰포트를 벗어나는 컨테이너를 잘라서 쓰지 않는다.** 클램프 방식은 캡처 면적이 스크롤 픽셀마다 달라져 설명 불가능해지고(P4) 잘린 맥락을 만든다(P5). 화면에 온전히 들어오지 않으면 폴백한다.
- **iframe 내부 요소에는 적용하지 않는다.** 게이트가 iframe 자신의 뷰포트 기준이라 top 뷰포트에서의 완전 포함을 보장할 수 없고, top 좌표 변환 이후 남는 검사는 교차 여부뿐이라 확장 rect가 top에서 잘린 채 저장된다(P4·P5 위반). 현행 방식 그대로 둔다.
- **`StyleChangesDialog` 행 초기화 재캡처에는 적용하지 않는다.** 이 경로는 요소도 selector로 재조회하므로 "현재 요소를 포함하는지" 재검증이 성립하지 않고(행 삽입·삭제 시 요소와 조상의 selector가 함께 밀린다), 요소만 화면 중앙으로 스크롤하므로 조상이 뷰포트 완전 포함을 거의 못 넘는다(P1).
- **요소 단일 캡처(element-shot)에는 적용하지 않는다.** `captureElementShot`(요소 측 스크린샷, `captureMode:"screenshot"`)은 diff가 아니라 "이 요소를 찍었다"는 의도가 명확해야 하므로 현행 유지. 확장은 element mode의 before/after 경로만 **명시적으로 opt-in**한다.
- **확장 발동률 계측(텔레메트리)을 추가하지 않는다.** PostHog 이벤트 추가는 `docs/privacy.{ko,en}.md` 수집 항목 갱신 트리거라 이번 스코프 밖이다. 대신 출시 전 실사이트 표본을 수동 관찰한다(성공 기준 참조).
- **AI 프롬프트 페이로드 정책을 다루지 않는다.** 확장 이미지가 커지면 AI 초안의 이미지 예산을 더 소모할 수 있으나, 예산 정책 조정은 별도 과제다.

## 사용자 시나리오

### S1. 다이얼로그 안 버튼 수정 (핵심)

1. 사용자가 모달 다이얼로그 안 버튼을 picker로 선택한다.
2. before 스냅샷 캡처 시 확장 판정이 돌아 다이얼로그 컨테이너를 찾고, 포함·면적 게이트를 통과하면 **다이얼로그 전체**가 캡처된다. 게이트를 통과하지 못하면 현행 방식으로 폴백한다.
3. 사용자가 버튼 색상을 수정한다.
4. `[다음]`은 before 캡처가 **날아가는 동안에만** 잠긴다. 일반 경로에서는 편집을 마칠 즈음 캡처가 이미 끝나 있어 이 잠금이 체감되지 않는다(S6이 실제 노출 창을 다룬다).
5. `[다음]`으로 진행하면 after 스냅샷이 **before와 같은 다이얼로그 컨테이너** 기준으로 캡처된다.
6. 이슈 본문의 before/after 표에 이미지 두 장이 들어가며, 사용자는 작성 화면에서 캡처 범위를 확인한 뒤 제출한다.

### S2. 테이블 셀 수정

1. 사용자가 테이블 행 안의 상태 배지를 선택한다.
2. 확장 판정이 `<tr>`을 찾고 게이트를 통과하면 **행 전체**가 캡처된다. 넓은 행 등 게이트를 통과하지 못한 경우 현행 방식으로 폴백한다.
3. 이슈 트래커에 업로드된 결과 이미지에서 리포트 수신자가 어느 행의 문제인지 식별할 수 있다.

### S3. 요소 제거 (`display:none`)

1. 사용자가 리스트 아이템 안 요소를 선택한다. before는 `<li>` 기준으로 캡처된다.
2. 사용자가 `display:none`으로 요소를 제거한다.
3. after 캡처 시 **before에서 확정한 `<li>`를 다시 측정**한다. 요소 rect가 0×0이라 기하적 포함 검사는 무의미하므로 DOM 포함(`ancestor.contains(el)`)으로 대체 검증하고, 뷰포트·면적 게이트는 그대로 적용한다. `<li>`는 여전히 렌더링되므로 rect가 정상이고, 요소가 빠져 레이아웃이 당겨진 모습이 담긴다.
4. 확장이 없었던 경우에도 before 시점의 scroll·viewport가 그대로면 저장된 before rect를 재사용해 의미 있는 이미지를 남긴다.
5. before/after를 나란히 보면 "이 요소가 빠지면 이렇게 된다"가 읽힌다.

### S4. 확장 실패 → 폴백 (정확도 보장)

1. 사용자가 시맨틱 컨테이너가 없는 `<div>` 체인 안의 요소를 선택한다.
2. 확장 신호가 잡히지 않아 **현행 방식(요소 bbox + 24px)** 으로 캡처된다.
3. 동작이 지금과 완전히 동일하다.

### S5. 과확장 차단

1. 사용자가 풀스크린 백드롭(`position:fixed; inset:0`) 안의 요소를 선택한다.
2. positioned-only 백드롭은 후보가 아니므로 확장이 시도되지 않는다.
3. 현행 방식으로 폴백해, 요소가 점처럼 보이는 이미지를 만들지 않는다.

### S6. 복수 요소 편집 (버퍼)

1. 사용자가 첫 요소를 편집하고 `다시 선택`으로 두 번째 요소로 넘어간다. 첫 요소는 버퍼에 담기고 캡처 기준도 함께 저장된다.
2. 사용자가 버퍼에 담긴 첫 요소를 다시 선택한다. 이 경로는 **before 캡처를 새로 돌리지 않는다**(편집된 DOM을 찍으면 before가 오염되므로). 저장된 before 이미지와 캡처 기준을 그대로 복원하고 `[다음]`은 즉시 활성이다.
3. 패널을 닫았다 열어 세션이 재바인딩되는 경우에도 캡처 기준이 함께 복원되어, before와 after가 서로 다른 기준으로 갈리지 않는다.

### 엣지 케이스

| 상황 | 기대 동작 |
|---|---|
| 모달 안 테이블 셀 | **최근접 우선** — `<tr>`이 선택된다(다이얼로그 아님) |
| 컨테이너가 뷰포트보다 큼 (긴 목록 항목·긴 `article`·모바일 뷰) | **면적과 무관하게 폴백** — 화면에 온전히 안 들어오면 확장하지 않는다 |
| 컨테이너가 일부라도 뷰포트 밖으로 스크롤됨 | 폴백. 잘린 컨테이너 이미지를 만들지 않는다 |
| before 후 사용자가 스크롤 | 저장한 컨테이너를 after 시점에 **재측정·재검증**한다. 게이트를 다시 통과하면 확장 유지, 실패하면 아래 순서로 강등 |
| 확장 성공했으나 after 시점에 컨테이너가 DOM에서 사라짐 | ① 저장된 before rect 재사용 시도(scroll·viewport 동일할 때만) → ② 요소 bbox 폴백 |
| 저장 selector가 DOM 변경 후 다른 노드를 가리킴 | 현재 요소 DOM 포함·게이트 재검증 실패 → 위와 같은 순서로 강등 |
| after가 폴백해 before와 프레이밍이 달라짐 | 허용한다. 각 이미지는 개별적으로 유효하다(P2) |
| 폴백 경로 + 요소가 `display:none` | before 시점의 scroll·viewport가 **모두 동일**하면 before rect 재사용. 하나라도 다르면 좌표를 신뢰할 수 없으므로 after 이미지 없음 |
| 요소가 DOM에서 detach돼 rect가 0×0 | 위와 동일 경로(0×0 폴백) |
| iframe 내부 요소 | **확장 미적용** — 현행 방식 그대로. 기존 top 좌표 변환 경로 유지 |
| `StyleChangesDialog` 행 초기화 재캡처 | **확장 미적용** — 현행 방식 그대로 |
| 요소 단일 캡처(element-shot) | **확장 미적용** — opt-in 플래그를 켜지 않는다 |
| 요소 자신이 `<li>`·`<tr>` | 자신은 후보에서 제외(확장 실익 0). 상위 단위를 찾거나 폴백 |
| before 캡처 지연 | 캡처가 날아가는 동안만 `[다음]` 잠금 |
| before 캡처 실패 | 캡처 기준을 비우고 잠금을 해제한다 — before 없이 진행하는 **현행 동작을 유지**한다 |
| 버퍼된 요소 재선택 | before 캡처를 돌리지 않는다. 저장된 이미지·기준 복원, `[다음]` 즉시 활성 |
| drafting에서 스타일링으로 복귀 | 기존 before 이미지와 캡처 기준을 함께 유지, `[다음]` 활성 유지 |
| 패널 닫았다 열기 (세션 rebind) | 캡처 기준이 세션 스냅샷·버퍼 승격 경로로 함께 복원된다 |
| 저장한 draft 재개 | optional 필드가 있으면 복원, 레거시 draft는 현행 폴백 |

## 성공 기준

**기능**

- 강한 시맨틱 후보가 **화면 완전 포함·요소 포함·면적** 게이트를 모두 통과하면 모달·테이블 행·리스트 항목의 before가 그 컨테이너를 담는다.
- after 재검증이 통과하면 before와 **같은 컨테이너**를 담는다.
- after 재검증이 실패하면 before rect 재사용 → 요소 bbox 순으로 강등하고, **잘못된 영역을 찍지 않는다.**
- 잘린 컨테이너 이미지를 만들지 않는다. 컨테이너를 담거나, 현행 방식으로 요소를 담거나 둘 중 하나다.
- 게이트를 통과하지 못한 후보와 제외된 폼·landmark·positioned 컨테이너·iframe·by-selector 재캡처·element-shot은 현행 방식으로 폴백한다.
- 안정된 컨테이너가 있거나 before 시점의 scroll·viewport가 그대로면 `display:none` after 이미지가 24×24 좌상단 조각이 되지 않는다. 그렇지 않으면 잘못된 이미지를 만드는 대신 이미지 없음으로 처리한다.
- 시맨틱 컨테이너가 없는 요소는 현행과 동일한 이미지가 나온다(회귀 없음).
- 확장된 이미지에서 편집 대상 요소가 항상 온전히 보인다(잘리지 않음).
- 확장 rect는 뷰포트 면적의 **40%** 를 넘지 않는다.

**예측 가능성**

- 같은 요소를 **같은 화면 상태**에서 고르면 항상 같은 판정이 나온다.
- 판정이 확장/폴백 두 값으로만 갈리고, 그 사이의 중간 크기 이미지는 나오지 않는다.

**무회귀**

- `[다음]`이 잠기는 구간은 before 캡처가 실제로 날아가는 동안뿐이다. 버퍼 재선택·`backToStyling`·세션 rebind·캡처 실패 경로에서는 잠기지 않는다.
- `next-step`을 쓰는 기존 e2e spec이 전부 통과한다.
- 기존 `src/store/__tests__/editor-store.test.ts`가 전부 통과한다.

**검증 게이트**

- `pnpm test` 통과 — `capture-context.test.ts`(게이트 산술)·`capture-context.test.tsx`(조상 탐색·after 재검증)·`editor-store.test.ts`(캡처 기준 생명주기) 포함.
- `pnpm test:e2e` 통과 — 신규 spec 3개(확장 / 폴백 / `[다음]` 잠금).
- `pnpm typecheck` 통과.

**수동 검증**

- **대표 fixture**: 모달(`[role="dialog"]` 안 버튼) · 테이블(반복 `<tr>` 안 배지) · 시맨틱 없는 `<div>` 체인 · 풀스크린 백드롭 4종을 담은 e2e 픽스처 페이지.
- 이슈 트래커에 업로드된 결과 이미지에서 대상 다이얼로그·행을 식별할 수 있다. (사이드패널 before/after 표는 이미지 실효 폭이 약 105px이라 범위 확인용이며, 세부 판독 기준으로 쓰지 않는다.)
- 확장 이미지에 인접 개인정보가 불필요하게 포함되지 않는다.
- 40% 상한을 넓은 모니터·좁은 창 양쪽에서 확인한다. 과확장이 관찰되면 낮추고, 발동률이 낮다는 이유로는 올리지 않는다.
- 출시 전 실사이트 표본(모달·테이블·리스트가 있는 페이지 여러 곳)에서 확장 발동을 관찰한다. 0건이면 게이트가 설계대로 도는지 점검하고 출시 가치를 재판단한다 — **게이트 완화 근거가 아니다.**
