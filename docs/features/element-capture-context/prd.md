# Element 캡처 컨텍스트 확장

## 배경

element mode는 요소 스타일을 편집하고 before/after 스냅샷을 이슈에 담는다. 두 스냅샷 모두 **요소 bbox + 24px 마진**으로만 크롭된다(`src/sidepanel/capture.ts:11`, `src/content/picker.ts:348`). 이 고정 규칙에서 두 가지 문제가 나온다.

**1. 맥락 소실.** 다이얼로그 안 버튼 하나를 수정하면 그 버튼만 찍힌다. 리포트를 받는 사람은 이 이미지가 어느 화면·어느 다이얼로그의 것인지 알 수 없다. 모달만의 문제가 아니다 — 테이블 셀을 고치면 어느 행인지, 리스트 아이템 안 요소를 고치면 어느 항목인지 식별할 수 없다. 특히 테이블 행 식별이 안 되는 리포트는 사실상 재현 불가다.

**2. `display:none` 캡처 깨짐.** 요소를 제거하는 수정에서 `getBoundingClientRect()`가 전부 0을 반환한다. rect가 `{0,0,0,0}`이 되어 크롭이 `(-24,-24,48,48)`로 계산되고, `clampCropRect`(`src/sidepanel/lib/crop-rect.ts`)가 이를 `(0,0,24,24)`로 가둔다. 결과적으로 **after 이미지가 페이지 좌상단 24×24 픽셀 조각**이 된다. `visibility:hidden`·`opacity:0`은 rect가 살아있어 빈 사각형이라도 나오지만, `display:none`은 완전히 무의미한 이미지가 나온다.

두 문제는 뿌리가 같다. 캡처 rect를 **요소 자신의 bbox로만** 잡는다는 것. 요소를 감싸는 의미 단위(다이얼로그·테이블 행·폼)로 rect를 넓히면 맥락이 살아나고, 조상은 `display:none`이 아니므로 rect가 정상이라 2번도 함께 해소된다.

## 설계 원칙 (이 기능의 판단 기준)

이 기능은 **버그 리포트의 증거물을 만드는 경로**를 건드린다. 잘못된 이미지가 담긴 리포트는 없는 것보다 나쁘다 — 받는 사람이 엉뚱한 곳을 보고 재현을 시도하기 때문이다. 그래서 아래 원칙이 편의성·커버리지보다 우선한다. **각 원칙은 개별 판단이 아니라 이 우선순위에서 파생된 결과다.**

### P1. 불확실하면 확장하지 않는다

확장 여부가 조금이라도 의심스러우면 현행 방식(요소 bbox + 24px)으로 폴백한다. "아마 이 컨테이너일 것"이라는 추정으로 확장하지 않는다. **커버리지 손실은 의도적으로 수용한 비용이다** — 확장이 안 걸리는 요소가 많아지는 것은 실패가 아니라 설계대로 동작하는 것이다.

### P2. 폴백은 현행 동작이므로 회귀 위험이 없다

모든 실패 경로(신호 없음·게이트 미달·selector 소실·rect 무효)가 **같은 출구**로 수렴한다. 확장이 실패하면 지금과 완전히 동일한 이미지가 나온다. 이 구조 덕분에 게이트를 아무리 조여도 기존 동작이 나빠지지 않는다. 반대로 게이트를 풀면 **새로운 실패 모드가 생긴다** — 비대칭적이므로 조이는 쪽이 항상 안전하다.

### P3. 신호는 구조적으로 확정된 것만 쓴다

`<tr>`이 테이블 행이라는 것, `[role="dialog"]`가 다이얼로그라는 것은 **오탐이 불가능한 사실**이다. 반면 "배경색이 있으니 카드일 것", "면적이 튀니 경계일 것", "`position:absolute`니 팝오버일 것"은 추정이다. 후자는 임계값 튜닝이 끝없고, 틀렸을 때 엉뚱한 영역이 찍혀 P1을 정면으로 위반한다. 커버리지를 늘리려고 추정 신호를 넣지 않는다.

### P4. 판정은 예측 가능해야 한다

같은 페이지에서 같은 요소를 고르면 **항상 같은 결과**가 나와야 한다. 스크롤 위치·창 크기 같은 우발적 상태가 확장 여부를 바꾸면, 사용자는 왜 어떤 때는 되고 어떤 때는 안 되는지 알 수 없고 재현도 못 한다. 이 원칙 때문에 "컨테이너를 뷰포트로 잘라서 판정"하는 방식을 버렸다.

### P5. 부분적 맥락보다 확실한 요소가 낫다

컨테이너가 화면에 다 안 들어와 잘린 이미지를 만드느니, 요소만 정확히 찍는 편이 낫다. 잘린 컨테이너는 맥락을 반만 주면서 이미지 크기 비용은 다 치른다. **"컨테이너 전체를 보여줄 수 있을 때만 컨테이너를 보여준다."**

### P6. 캡처 범위 확대는 프라이버시 확대다

BugShot의 코어 밸류는 클라이언트 온리 프라이버시다(`CLAUDE.md`). 캡처 범위를 넓히면 선택 요소 주변의 고객 데이터가 이미지에 더 들어간다. 후보를 강한 시맨틱으로 제한하고 인접 개인정보를 넓게 포함하는 컨테이너(`form`·landmark)를 제외한 것은 이 이유이기도 하다. 사용자가 작성 화면에서 결과 이미지를 확인한 뒤 제출하는 기존 검토 단계가 마지막 안전망이다.

---

**리뷰어에게**: 위 원칙에서 파생된 결정(게이트 강도, 신호 목록, 하이라이트·범위 조절 UI 제외, 뷰포트 완전 포함 요구)은 이미 검토를 거쳤다. 완화를 제안하려면 **어느 원칙을 어떤 근거로 뒤집는지** 명시해야 한다. "커버리지가 낮다"·"확장이 잘 안 걸린다"는 그 자체로는 완화 근거가 아니다 — P1에서 이미 수용한 비용이다.

## 목표

- 요소를 감싸는 **의미 단위 컨테이너**를 신뢰할 수 있는 신호로 식별해, 확신이 있을 때만 캡처 rect를 그 경계로 확장한다.
- 확장 조건에 하나라도 미달하면 **현행 방식(요소 bbox + 24px)으로 폴백**한다. 리포트 정확도를 해칠 수 있는 경로를 만들지 않는다.
- `display:none` 등으로 요소 rect가 0이 되어도 의미 있는 after 이미지를 남긴다.
- before/after가 **같은 컨테이너**를 기준으로 찍혀, 두 이미지의 비교 대상이 일치한다.
- 자동 확장으로 선택 요소 주변의 고객 데이터가 더 포함될 수 있음을 제품 trade-off로 다룬다. 후보를 강한 시맨틱으로 제한하고, 사용자가 작성 화면에서 결과 이미지를 확인한 뒤 제출하는 기존 검토 단계를 안전망으로 삼는다.

## 비목표 (Non-goals)

- **하이라이트 오버레이를 그리지 않는다.** 편집한 요소를 이미지에 사각형으로 표시하는 기능은 이번 스코프에서 제외한다. 대신 면적 게이트로 과확장 자체를 막아 요소가 점처럼 작아지는 상황을 만들지 않는다.
- **캡처 범위 조절 UI를 추가하지 않는다.** 사용자가 확장 범위를 넓히거나 좁히는 컨트롤은 만들지 않는다. 자동 판정이 틀리면 폴백으로 수렴하므로 복구 수단이 따로 필요하지 않다(P2).
- **시각 휴리스틱을 쓰지 않는다.** 배경색·border·box-shadow·border-radius·면적 점프 비율은 추정 신호라 채택하지 않는다(P3).
- **positioned 휴리스틱을 쓰지 않는다.** `position:absolute|fixed` + `z-index`만으로는 의미 단위를 보장할 수 없다(P3). 시맨틱 없는 커스텀 팝오버·백드롭은 폴백한다.
- **시맨틱이 없는 컨테이너를 추론하지 않는다.** `<div class="card">` 같은 커스텀 패널은 확장 대상이 아니며 폴백된다(P3). 알려진 한계로 수용한다.
- **폼·광범위 landmark를 자동 확장하지 않는다.** `form`·`section`·`nav`·`aside`·`header`·`footer`·`[role="group"]`는 인접 개인정보를 넓게 포함하거나 의미 경계가 모호하다(P6).
- **뷰포트를 벗어나는 컨테이너를 잘라서 쓰지 않는다.** 클램프 방식은 스크롤 위치가 판정을 바꾸고(P4) 잘린 맥락을 만든다(P5). 화면에 온전히 들어오지 않으면 폴백한다.
- **요소 단일 캡처(element-shot)에는 적용하지 않는다.** `usePickerMessages.ts:90`의 `captureElementShot`(요소 측 스크린샷, `captureMode:"screenshot"`)은 diff가 아니라 "이 요소를 찍었다"는 의도가 명확해야 하므로 현행 유지.

## 사용자 시나리오

### S1. 다이얼로그 안 버튼 수정 (핵심)

1. 사용자가 모달 다이얼로그 안 버튼을 picker로 선택한다.
2. before 스냅샷 캡처 시 확장 판정이 돌아 다이얼로그 컨테이너를 찾고, 포함·면적 게이트를 통과하면 **다이얼로그 전체**가 캡처된다. 게이트를 통과하지 못하면 현행 방식으로 폴백한다.
3. 사용자가 버튼 색상을 수정한다.
4. before 캡처가 확정되기 전에는 `[다음]`이 비활성화된다. 캡처 성공 또는 현행 방식 폴백이 확정된 뒤 진행할 수 있다.
5. `[다음]`으로 진행하면 after 스냅샷이 **before와 같은 다이얼로그 컨테이너** 기준으로 캡처된다.
6. 이슈 본문의 before/after 표에 이미지 두 장이 들어가며, 사용자는 작성 화면에서 캡처 범위와 민감정보 포함 여부를 확인한 뒤 제출한다.

### S2. 테이블 셀 수정

1. 사용자가 테이블 행 안의 상태 배지를 선택한다.
2. 확장 판정이 `<tr>`을 찾고 게이트를 통과하면 **행 전체**가 캡처된다. 넓은 행 등 게이트를 통과하지 못한 경우 현행 방식으로 폴백한다.
3. 리포트 수신자가 어느 행의 문제인지 식별할 수 있다.

### S3. 요소 제거 (`display:none`)

1. 사용자가 리스트 아이템 안 요소를 선택한다. before는 `<li>` 기준으로 캡처된다.
2. 사용자가 `display:none`으로 요소를 제거한다.
3. after 캡처 시 **before에서 확정한 `<li>`를 다시 측정**한다. `<li>`는 여전히 렌더링되므로 rect가 정상이고, 요소가 빠져 레이아웃이 당겨진 모습이 담긴다.
4. before/after를 나란히 보면 "이 요소가 빠지면 이렇게 된다"가 읽힌다.

### S4. 확장 실패 → 폴백 (정확도 보장)

1. 사용자가 시맨틱 컨테이너가 없는 `<div>` 체인 안의 요소를 선택한다.
2. 확장 신호가 잡히지 않아 **현행 방식(요소 bbox + 24px)** 으로 캡처된다.
3. 동작이 지금과 완전히 동일하다.

### S5. 과확장 차단

1. 사용자가 풀스크린 백드롭(`position:fixed; inset:0`) 안의 요소를 선택한다.
2. positioned-only 백드롭은 후보가 아니므로 확장이 시도되지 않는다.
3. 현행 방식으로 폴백해, 요소가 점처럼 보이는 이미지를 만들지 않는다.

### 엣지 케이스

| 상황 | 기대 동작 |
|---|---|
| 모달 안 테이블 셀 | **최근접 우선** — `<tr>`이 선택된다(다이얼로그 아님) |
| 컨테이너가 뷰포트보다 큼 (긴 목록 항목·긴 `article`·모바일 뷰) | **면적과 무관하게 폴백** — 화면에 온전히 안 들어오면 확장하지 않는다 |
| 컨테이너가 일부라도 뷰포트 밖으로 스크롤됨 | 폴백. 스크롤 위치가 확장 여부를 바꾸지 않는다 |
| before 후 사용자가 스크롤 | 저장한 컨테이너를 after 시점에 **재측정·재검증**하므로 확장 경로는 영향 없음 |
| 확장 성공했으나 after 시점에 컨테이너가 DOM에서 사라짐 | 폴백 경로로 전환 |
| 저장 selector가 DOM 변경 후 다른 노드를 가리킴 | 현재 요소 포함·면적 게이트 재검증 실패 → 폴백 |
| 폴백 경로 + 요소가 `display:none` | viewport가 유지됐으면 before rect 재사용. 스크롤·viewport 변경으로 좌표 신뢰가 없으면 after 이미지 없음 |
| iframe 내부 요소 | 조상 탐색은 iframe 문서 안에서 끝난다. 기존 top 좌표 변환 경로 그대로 |
| 요소 자신이 `<li>`·`<tr>` | 자신은 후보에서 제외(확장 실익 0). 상위 단위를 찾거나 폴백 |
| before 캡처 지연 | 캡처 기준이 확정될 때까지 `[다음]` 비활성화 |
| before 캡처 실패 | 기존 실패 안내를 유지하고 `[다음]`을 비활성화해 기준 없는 after 캡처를 막음 |
| drafting에서 스타일링으로 복귀 | 기존 before 이미지와 캡처 컨텍스트를 함께 유지 |
| 저장한 draft 재개 | optional 컨텍스트가 있으면 복원, 레거시 draft는 현행 폴백 |

## 성공 기준

- 강한 시맨틱 후보가 **화면 완전 포함·요소 포함·면적** 게이트를 모두 통과하면 모달·테이블 행·리스트 항목의 before·after가 같은 컨테이너를 담는다.
- 확장 결과가 **스크롤 위치에 의존하지 않는다** — 같은 요소를 같은 페이지 상태에서 고르면 어디까지 스크롤했든 같은 판정이 나온다.
- 잘린 컨테이너 이미지를 만들지 않는다. 컨테이너를 담거나, 현행 방식으로 요소를 담거나 둘 중 하나다.
- 게이트를 통과하지 못한 후보와 제외된 폼·landmark·positioned 컨테이너는 현행 방식으로 폴백한다.
- 안정된 컨테이너가 있거나 동일 viewport의 before rect를 신뢰할 수 있으면 `display:none` after 이미지가 24×24 좌상단 조각이 되지 않는다. 그렇지 않으면 잘못된 이미지를 만드는 대신 이미지 없음으로 처리한다.
- 시맨틱 컨테이너가 없는 요소는 현행과 동일한 이미지가 나온다(회귀 없음).
- 확장된 이미지에서 편집 대상 요소가 항상 온전히 보인다(잘리지 않음).
- 확장 rect는 대표 모달·테이블과 넓은/좁은 viewport 실측에서 확정한 상한을 넘지 않는다. 초기 제안값은 뷰포트 면적의 40%다.
