# 감사 후속 정비 (Audit Remediation)

## 배경

2026-07-26 `/audit` 전체 코드베이스 감사(4개 전문 에이전트 + 하위 Explore 16개, 비테스트 소스 441개 사실상 전수)에서 **63건**의 발견이 나왔다 — 🔴 9 · 🟡 37 · ⚪ 17.

이건 기능 추가 트랙이 아니라 **이미 진단된 결함을 항목별로 닫는 정비 트랙**이다. 한 번에 일괄 수정하면 안 되는 이유가 셋 있다:

1. **63건이 한 diff에 들어가면 회귀 귀속이 불가능하다.** e2e가 빨개졌을 때 어느 항목이 범인인지 못 가린다. 특히 이 저장소는 `docs/POSTMORTEM.md`가 반복 경고하듯 **content script·picker·캡처 경로의 회귀가 단위 테스트로도 e2e로도 안 잡히는 구간**(포인터 드래그, pointer capture 암묵 해제, 실 Chrome 탭 주입)을 갖고 있다.
2. **발견 중 일부는 "고칠 수 있다"이지 "고쳐야 안전하다"가 아니다.** 마스킹 강화는 재현에 필요한 값을 죽일 수 있고(POSTMORTEM 2026-07-14가 정확히 이 오탐을 회고한다), `redirect:"manual"`은 정상 BYOK 게이트웨이의 리다이렉트를 깨며, frameToken 노출은 설계 교체 없이는 못 닫는다.
3. **일부 "당연해 보이는 수정"은 명시적 불변식을 깬다.** FIFO 캡 상수를 공용 모듈로 중앙화하면 `recorders-entry` 청크에 외부 static import가 유입돼 **crxjs 동기 IIFE emit이 깨지고 pre-arm이 무력화**된다(ARCHITECTURE "동기 IIFE emit"). URL 경로에 `encodeURIComponent`를 일괄 적용하면 GitLab의 이미 URL-encoded된 project path가 **이중 인코딩**된다.

그래서 발견을 "고칠 목록"이 아니라 **"항목별로 재현 → 그물 → 수정 → 검증"의 추적 단위**로 떨군다.

## 목표

- 63건 각각이 **독립적으로 검증 가능한 태스크**로 존재한다 — 재현/검증 방법, 수정 방향, 회귀 테스트, 리스크가 항목마다 명시된다.
- **그물이 수정보다 먼저 간다.** 감사가 드러낸 두 개의 구조적 사각지대(log-viewer 복제 사전의 공용 컴포넌트 키 미스캔, `pruneOrphanBlobs` 무테스트)를 먼저 닫아, 이후 수정이 회귀를 만들면 테스트가 잡는다.
- **설계 결정이 필요한 항목이 코드 수정과 분리**된다 — 합의 전에 코드가 먼저 나가지 않는다.
- 웨이브 단위로 **커밋·e2e 게이트를 끊을 수 있다** — 한 웨이브가 e2e 빨강을 내면 그 웨이브만 되돌린다.
- 각 항목이 `docs/POSTMORTEM.md`의 기존 회고와 **어떤 관계인지**(재발인지, 새 함정인지) 기록된다.

## 비목표 (Non-goals)

- **이 문서 단계에서의 코드 수정** — `src/`·`manifest.config.ts`·`package.json` 일체 변경하지 않는다.
- **구조 리팩터** — `DraftDetailDialog`/`IssueCreateModal`의 8종 submit 핸들러 통합(A-40), `*SubmittedBadge` 폴링 훅 추출(A-41), `ai-provider.ts`·`buildIssueMarkdown.ts`·`picker-control.ts`·`messages.ts` 모듈 분할(A-45)은 **정비 트랙 밖**이다. CLAUDE.md "요청하지 않은 유연성·추상화 추가 금지"에 걸리고, 핵심 파일이 통째로 바뀌면 e2e 회귀 귀속이 불가능해진다. 별도 트랙으로 승격 여부만 기록한다.
- **oauth-proxy 인프라 변경** — rate limit은 KV/Durable Object 바인딩 + 배포 변경이라 코드 정비가 아니다. 코드로 닫히는 부분(와일드카드 Origin 거부, Atlassian 핸들러 가드)만 이 트랙에 넣는다.
- **기존 dead code 삭제** — CLAUDE.md "기존 dead code는 언급만 하고 삭제하지 않는다". 목록으로만 남긴다.
- **감사 재실행** — 63건은 확정 입력이다. 새 발견을 찾지 않는다.

## 사용자 시나리오

정비 트랙의 "사용자"는 이 저장소에서 작업하는 개발자다.

**S1 — 웨이브 단위 실행**
1. `tasks.md`에서 웨이브를 하나 고른다(W0부터 순서대로).
2. 그 웨이브의 각 항목에 대해 **재현 테스트를 먼저 박아 red를 확인**한다(TDD 강제 대상만 — 분류는 항목에 명시).
3. 수정해 green으로 전환한다.
4. `pnpm test --run` + `pnpm typecheck` 통과를 확인하고 **웨이브 단위로 커밋**한다.
5. `/e2e-run`으로 회귀를 확인한 뒤 다음 웨이브로 간다.

**S2 — 설계 결정 항목 진입**
1. W2 항목(A-04 frameToken, A-08 rate limit, A-20 http 허용, A-32 ActionEntry union, A-12 setItem 실패 전파)은 **수정 방향이 확정돼 있지 않다.**
2. 각 항목에 정리된 선택지·트레이드오프를 읽고 방향을 정한다.
3. 방향이 정해진 뒤에만 W1~W6과 같은 절차로 진입한다. 정하지 못하면 그 항목은 열린 채로 남는다 — **보류가 정상 종료 상태다.**

**S3 — 회귀 발생 (엣지 케이스)**
1. 어느 웨이브 커밋 후 `/e2e-run`이 빨개진다.
2. 웨이브 단위로 커밋했으므로 그 커밋만 되돌리고, 항목별로 쪼개 재시도한다.
3. 원인이 비자명한 함정이었으면 `/postmortem`으로 `docs/POSTMORTEM.md`에 회고를 남긴다.

**S4 — 항목이 이미 해소돼 있음 (엣지 케이스)**
- 착수 시점에 코드가 이미 바뀌어 재현 테스트가 처음부터 green이면, 그 항목은 **"재현 불가 — 해소됨"으로 닫고** 테스트는 남긴다(회귀 자산).
