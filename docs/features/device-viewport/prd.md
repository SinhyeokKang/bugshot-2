# 디바이스 뷰포트 (device viewport)

## 배경

반응형 버그는 폭이 좁아졌을 때만 재현된다. 지금 BugShot으로 그 버그를 잡으려면 사용자가 **브라우저 창 자체를 줄여야** 하고, 그러면 사이드패널이 페이지를 더 밀어내서 실제 폭을 통제할 수 없다. 결국 DevTools device toolbar를 따로 켜게 되는데, 그 순간 BugShot의 캡처·로그 수집과 화면이 분리된다.

목적은 **BugShot 안에서 폭을 고정한 채 캡처·로그·리포트까지 한 흐름으로 끝내는 것**이다. 사용자의 실제 사용 패턴은 "디버깅 시작 전에 모바일 환경을 셋업해두고 TC 한 세트를 돈다"이므로, 모드 진입 시의 페이지 재로드는 비용이 아니라 셋업의 일부다.

### 구현 방식이 제품 범위를 결정한다

`debugger` 권한을 취득하지 않는다는 것이 확정 제약이다. 이 하나가 기능 범위를 규정한다.

| 축 | 에뮬레이트 | 이유 |
|---|:---:|---|
| 뷰포트 폭 (`innerWidth`, `vw`) | ✅ | iframe 뷰포트가 곧 폭 |
| 미디어쿼리 브레이크포인트 | ✅ | iframe이 독립 뷰포트라 정상 발화 |
| `position: fixed` | ✅ | iframe 내부에서 정상 |
| `devicePixelRatio` (2x/3x `srcset`) | ❌ | CDP `Emulation.setDeviceMetricsOverride` 없이는 불가 |
| 터치 이벤트, `pointer: coarse`, `maxTouchPoints` | ❌ | 동일 |
| `navigator.userAgent` | ❌ | JS 프로퍼티는 CDP 없이 불가. DNR로 요청 헤더만 바꾸면 서버는 모바일 HTML, 클라이언트 JS는 데스크톱 분기라는 불일치가 생긴다 — 그래서 DNR도 안 쓴다 |

따라서 이 기능의 이름은 "디바이스 에뮬레이션"이 아니라 **"뷰포트 폭 기반 반응형 검증"** 이다. UA 스니핑으로 분기하는 사이트는 데스크톱 레이아웃을 그대로 낸다. 프리셋 라벨을 `iPhone 14`가 아니라 **폭 숫자(`390`)로 두는 것도 같은 이유** — 없는 것을 있다고 말하지 않는다. 기기 아이콘은 스캔성을 위한 **보조 기호**일 뿐이고 숫자를 대체하지 않는다.

### 방식: 인페이지 iframe 래핑

현재 탭 문서 안에 같은 URL을 로드하는 iframe을 만들고, 원본 body 자식을 숨긴 뒤 그 iframe을 디바이스 폭으로 렌더한다. 래퍼는 top과 same-origin이라 그 origin의 쿠키·스토리지를 그대로 쓴다.

**"래퍼는 언제나 top과 same-origin"이 이 기능의 불변식이다.** 래퍼가 cross-origin으로 나가려 하면 프레임 안에 두지 않고 **top 탭 자체를 그 URL로 보낸 뒤 같은 폭으로 모드를 재수립한다**(아래 S6).

가장 큰 이유는 **cross-site iframe이 사용자가 보는 것과 다른 화면을 낸다**는 것이다. Chrome의 third-party storage partitioning으로 localStorage·sessionStorage·IndexedDB가 top-level site 키로 파티션된 빈 저장소를 보고, SameSite=Lax(기본값) 쿠키도 실리지 않아 **로그아웃 상태로 렌더된다.** 그 화면을 찍으면 리포트의 재현 정보가 틀린다.

**판정 기준은 site가 아니라 origin이다** — 파티셔닝 자체는 site 키인데도 한 단계 좁게 잡는다. `a.com` → `www.a.com`처럼 same-site이면서 cross-origin인 경우 파티셔닝은 안 걸리지만 `window.frameElement`가 `null`이 되고 pre-arm 플래그(`sessionStorage`, origin 스코프)도 갈려서, same-origin 전제로 싸게 만든 배선 셋(래퍼 자가 식별·pre-arm 버퍼링·element 컨텍스트 확장)이 한꺼번에 무너진다. origin 기준이면 그 셋이 예외 없이 성립하고 대가는 서브도메인 이동에서 재로드 1회뿐이다.

부수 효과로 cross-origin 문서를 DOM 없이 추적하기 위한 계보 로직이 필요 없어진다. 래퍼 식별은 `device.frameReady` 등록 후 Chrome `frameId`/`documentId`가 맡는다. 기각된 대안과 근거는 design.md "대안 검토" 참조.

## 목표

1. **Debug > 이슈 작성 서브탭의 세그먼티드 컨트롤에서 뷰포트 폭을 고른다.** `[전체][390][768][1024]` 4세그먼트. 기본은 `전체`. 각 세그먼트는 기기 아이콘(`Monitor`/`Smartphone`/`Tablet`/`Laptop`)과 폭 숫자를 **병기**한다 — 아이콘만 두면 DPR·터치·UA까지 에뮬레이트한다는 오해가 생기므로 진실값인 폭 숫자를 지우지 않는다.
2. 폭을 고르면 페이지가 그 폭으로 다시 렌더되고, **미디어쿼리 브레이크포인트가 실제로 발화**한다. 페이지 자신의 `window.innerWidth`가 선택한 폭과 같다.
3. `전체`로 되돌리면 원래 페이지로 복귀한다.
4. **모드 ON에서 수집되는 console/network 로그는 1벌이다.** 숨겨진 원본 문서의 로그가 섞이지 않는다.
5. **모드 ON에서 캡처한 이슈의 재현 환경 `Viewport` 값은 사용자가 본 폭이다.** 브라우저 창 크기로 덮이지 않는다. 캡처 5종(element·screenshot·freeform·video·30s replay) **전부**에 적용된다 — 영상·리플레이는 `getTopViewport`가 아니라 `chrome.tabs.get()`을 쓰고 있어 별도 교체가 필요하다(design.md "뷰포트 값 파생"). 단 영상·리플레이 경로의 검증 수단은 e2e가 아니라 **단위 + 수동**이다(tasks.md Task 15 — 30s Replay 캡처는 suite 정책상 e2e 제외).
6. **`전체`(기본값)일 때 BugShot은 지금과 100% 동일하게 동작한다.** iframe을 만들지 않고, 프레임 트리·URL·frameId가 전부 오늘과 같다. 이것이 1급 요구사항이다.
7. 브라우저 창이 좁아 렌더할 수 없는 프리셋은 **비활성 + 이유 툴팁**으로 표시하고, 창을 키우면 자동으로 활성화된다.
8. 페이지 재로드와 중복 실행이 위험한 화면(제출 결과·결제 완료)을 위해 **최초 ON 진입 때 1회 확인 다이얼로그**를 띄운다. [계속]을 누르면 `chrome.storage.local`에 기록해 다시 띄우지 않는다.
9. iframe 삽입이 차단되는 사이트(XFO `DENY` / CSP `frame-ancestors 'none'`)에서 **자동 롤백**한다. 사용자가 백지 화면에 갇히지 않는다. **진입 시점뿐 아니라 모드 유지 중 발생한 차단도 같은 경로로 복구한다** — 감시창 안에서만 판정하면 래퍼 안 링크 이동으로 차단 사이트에 도달했을 때 백지에 방치된다.
10. **래퍼가 cross-origin으로 나가면 top 탭을 그 URL로 보내고 같은 폭으로 모드를 재수립한다**(= 새 디버깅 세션). 사용자가 주소창으로 직접 이동한 경우와 **동일하게 취급**한다 — 두 경로에 다른 규칙을 두지 않는다.
11. **모드 ON에서도 element 캡처의 의미 단위 조상 컨테이너 확장이 동작한다.** 확장 판정이 조용히 꺼지면 반응형 버그(컨테이너 넘침·줄바꿈 깨짐)에서 가장 필요한 범위가 사라진다.

## 비목표 (Non-goals)

- **`debugger` 권한 취득.** 어떤 경우에도 하지 않는다. 따라서 DPR·터치·UA 에뮬레이션은 영구 범위 밖이다.
- **브라우저 윈도우 크기 조작.** `chrome.windows.update`로 창을 줄이지 않는다.
- **DNR / `declarativeNetRequest` 권한.** UA 헤더 치환·XFO 제거 둘 다 안 한다. 새 권한은 0개다.
- **복수 디바이스 동시 표시.** 현재 탭 하나의 뷰포트만 제어한다.
- **디바이스 베젤·OS 상태바 렌더.** 스크린샷에 섞이면 리포트 품질만 떨어진다.
- **1차에서 제외한 부가 기능** — 아래 "2차 이후" 절 참조.

## 1차 릴리스 범위

### 포함

- 세그먼티드 컨트롤 4개(`전체` + 프리셋 3개), 기기 아이콘 + 폭 숫자 병기, 가용 폭 초과 비활성
- 래퍼 생성·제거·자동 롤백. `전체` 복귀도 재로드로 대칭시킨다. 차단 판정은 진입 시점과 모드 유지 중 **양쪽 모두**
- **cross-origin handoff** — 래퍼가 cross-origin으로 나가면 top을 그 URL로 보내고 같은 폭으로 재수립
- **재수립 단일 계약** — handoff·차단 복구·확장 reload 복구 셋이 한 함수(`reestablish`)를 쓴다. 사용자 전이(`select`)와 달리 `phase !== "idle"` 잠금을 우회하고, 1회 경고를 안 띄우며, 루프 카운터를 올린다(design.md "재수립 계약")
- **루프 가드** — 연속 재수립 2회 초과 또는 직전 재수립 URL 재방문이면 다이얼로그 → 모드 해제 + 이슈 idle. handoff가 아니라 재수립을 세야 frame-busting까지 잡힌다
- **element 컨텍스트 확장을 래퍼에서 유지** — `window === window.top` 게이트를 `top || 래퍼`로 연다
- 전 document 정지 → 래퍼 서브트리만 활성(로그 2벌 해소). sentinel 재발행 경로 전체가 같은 게이트를 통과한다 — 게이트가 하나라도 새면 숨겨진 원본 문서의 레코더가 되살아난다
- 모드 전환 시 로그 경계(`sync` + settle → clear)
- `Viewport` 환경 메타를 디바이스 폭으로 오버라이트 — **캡처 5종 전부**(영상·리플레이 포함)
- 화면(뷰포트) 캡처 rect를 래퍼 영역으로 보정 + **영역 드래그 rect를 래퍼 영역으로 클램핑**
- 페이지 전체 캡처 **잠금**(비활성 + 툴팁)
- 작성 화면 재현 환경 근처에 **모드 ON 읽기전용 인디케이터 1개** — 캡처 이후 구간에서 뷰포트 행이 사라져 ON 신호가 0이 되는 것을 막는다
- 래퍼 내부 **same-origin** 네비게이션을 top 네비게이션과 동등 취급(로그·세션 수명주기 동일화). cross-origin은 위 handoff가 받는다
- 2-depth 안내 다이얼로그 문구를 모드 ON 전용으로 분기
- 최초 ON 진입 1회 경고 — 재로드뿐 아니라 숨겨진 원본과 래퍼가 동시에 실행되어 네트워크 요청·자동저장·결제 동작이 중복될 수 있음, 그리고 다른 사이트로 이동하면 페이지 전체가 그 사이트로 다시 열림을 명시
- 녹화·미리보기·완료 phase에서 handoff가 나면 **비침습 토스트 1개**(사이트 변경으로 로그 초기화됨). 이 세 화면엔 다이얼로그 마운트 지점이 없다

### 제외 (2차 이후)

| 항목 | 미루는 이유 |
|---|---|
| **마지막 선택 폭 영속** | `chrome.storage`에 영속하면 "탭 reload로 래퍼가 사라졌는데 UI는 ON"이라는 desync 축이 생긴다 — 복원 경로가 페이지 DOM을 검증하지 않기 때문이다. 1차의 인메모리 `pending`은 이것과 다르다: 한 커밋만 살고, 매 top 커밋마다 실제 re-mount로 조정되며, 차단이면 `전체`로 롤백된다. 그 셋 중 하나라도 깨지면 이 항목의 desync가 되살아난다 |
| **회전(가로/세로) 토글** | 높이를 창 높이에 종속시키기로 했으므로 회전이 "더 넓은 폭 지정"과 같아져 의미가 약하다 |
| **커스텀 폭 직접 입력** | 세그먼티드 컨트롤에 input을 넣을 자리가 없어 행이 하나 더 붙거나 팝오버가 필요하다 |
| **모드 ON 상시 배지(전역)** | 연동·설정 탭에서도 상태를 보여주려면 전역 상태가 필요한데, 1차의 "페이지 DOM이 단일 출처" 구조와 충돌한다. 1차는 작성 화면 인디케이터 1개로 갈음한다 — `device.state.width != null`에서 파생하므로 전역 상태를 안 만든다 |
| **페이지 전체 캡처 래퍼 라우팅** | 오케스트레이터 frameId 인자화 + 타일 계획 보정 + 스티칭 폭 크롭 3점이 붙고, 전부 픽셀 판정이라 유닛으로 못 고정한다 |
| **높이 독립 지정 / zoom 슬라이더** | iframe에 `transform: scale`을 걸면 영역 캡처 크롭 배율과 드래그 좌표에 보정이 전부 딸려온다 |

## 사용자 시나리오

### S1. 반응형 버그 리포트 (주 흐름)

1. 사이드패널을 열고 Debug > 이슈 작성에 머문다. 뷰포트 행은 `전체`가 선택돼 있다.
2. `390`을 누른다 → 최초 ON 진입 1회 확인 다이얼로그(재로드와 원본·래퍼 동시 실행에 따른 중복 요청·자동저장·결제 위험) → [계속].
3. 페이지가 390px 폭으로 다시 렌더된다. 좌우는 중립 배경으로 채워진다.
4. 모바일 레이아웃에서 버그를 재현한다. 콘솔·네트워크 로그는 래퍼 프레임에서만 수집된다.
5. [요소 캡처] 또는 [범위 캡처] > 화면으로 캡처한다.
6. 작성 화면의 재현 환경에 `Viewport 390×<창높이>`가 들어가고, 그 옆에 접근 가능한 `뷰포트 390px` 인디케이터가 보인다.
7. 이슈를 제출한다.

### S2. 데스크톱으로 복귀

1. 뷰포트 행에서 `전체`를 누른다.
2. 래퍼가 제거되고 원본 페이지가 **재로드**된다 — 진입과 대칭이다. DOM 제거만 하면 모드 ON에서 한 로그인·장바구니 조작이 복귀 화면에 안 보여 상태가 어긋난다.
3. 로그가 초기화되고 이후 캡처는 브라우저 실제 폭을 기록한다.

### S3. 창이 좁을 때

1. 브라우저 창 1280px + 사이드패널 400px → 가용 폭 약 865px.
2. `1024` 세그먼트가 흐리게 표시되고, 툴팁이 "창이 좁아 사용할 수 없습니다"를 말한다.
3. 사이드패널을 좁히거나 창을 키우면 세그먼트가 **자동으로 활성화**된다(별도 새로고침 불필요).

### S4. iframe 삽입이 차단된 사이트

1. `390`을 누른다.
2. 3초 안에 래퍼가 자기 URL을 로드하지 못한다(XFO `DENY` / CSP `frame-ancestors 'none'`).
3. 래퍼를 제거하고 원본을 복원한 뒤 세그먼트를 `전체`로 되돌린다.
4. 토스트: "이 사이트는 디바이스 모드를 지원하지 않습니다(프레임 삽입 차단)".

> **redirect는 차단이 아니다.** same-origin redirect로 로드에 성공했으면 정상 진입이고, 목적지가 cross-origin이면 차단이 아니라 handoff(S6)로 간다. 차단 판정에 redirect를 합치면 정상 사이트가 오탐된다(design.md "로드 검증").

### S5. 모드 ON에서 iframe이 있는 페이지의 요소 선택 (알려진 제약)

1. 모드 ON에서 [요소 스타일 편집]으로 페이지 안의 iframe(광고·결제 위젯 등)을 클릭한다.
2. 그 iframe은 래퍼 기준 2-depth라 선택 불가다 — 기존 거부 경로(`picker.iframeUnsupported`)가 그대로 발화한다.
3. 안내 다이얼로그가 뜨되 문구는 **"디바이스 모드를 끄면 선택할 수 있습니다"** 로 바뀐다.

### S6. 래퍼 안에서 다른 사이트로 이동 (cross-origin handoff)

1. 모드 ON(390)에서 래퍼 안의 외부 링크를 눌러 다른 origin으로 이동한다.
2. 프레임 안에 두지 않고 **top 탭을 그 URL로 보낸다**. 페이지 전체가 그 사이트로 열린 뒤 같은 폭(390)으로 래퍼가 다시 만들어진다.
3. 로그는 초기화된다 — 실제 top cross-origin 네비게이션이라 기존 `logClear` 그물이 그대로 돈다.
4. 작성 중인 이슈가 있었으면 기존 **세션 만료 다이얼로그**(`페이지가 변경되었습니다`)가 뜨고, [확인]에서 draft가 초기화되며 이슈 idle로 돌아간다. 문구만 디바이스 모드용으로 갈린다.
5. idle이었으면 다이얼로그 없이 로그만 조용히 비워진다 — 오늘의 top 이동 동작과 같다.
6. 새 사이트가 프레임 삽입을 막으면 재수립이 차단되고 `전체`로 롤백 + 토스트(S4와 같은 경로).

> **주소창 이동도 같은 규칙이다.** 모드 ON에서 사용자가 top을 직접 다른 URL로 옮겨도 같은 폭으로 재수립한다. 폭은 사이드패널 인메모리에만 들고(영속하지 않는다) 매 top 커밋마다 실제 re-mount로 조정되므로, "래퍼는 없는데 UI만 ON"인 desync는 생기지 않는다.

### 엣지 케이스

| 상황 | 동작 |
|---|---|
| 캡처 진행 중·작성 중·녹화 중 (`phase !== "idle"`) | 세그먼티드 컨트롤 전체 비활성 — **사용자가** 전환을 일으켜 draft·선택 요소·녹화 스트림을 깨는 축을 차단한다. 페이지가 스스로 갈린 뒤의 재수립은 이 잠금을 우회하고, draft 파괴는 세션 만료 다이얼로그가 통보한다 |
| 미지원 페이지 (`chrome://` 등) | 뷰포트 행 자체를 렌더하지 않는다. 기존 캡처 버튼 은닉과 같은 게이트 |
| 모드 ON에서 top 탭이 다른 URL로 이동 | 래퍼가 소실되지만 **같은 폭으로 재수립**한다(S6과 동일 규칙). 미지원 URL로 갔으면 pending을 버리고 행 자체를 안 그린다 |
| 모드 ON 중 확장 reload·업데이트 | 프레임 추적 정보가 소실되고 페이지의 content script도 전부 무효화된다 → 사이드패널이 같은 폭으로 모드를 **재수립**(래퍼 재생성)한다. 페이지가 한 번 더 로드된다 |
| 모드 ON에서 래퍼 안의 **same-origin** 링크로 이동 | top 네비게이션과 동등 취급 — 떠나는 페이지 로그 꼬리 sync + reload면 `logClear`. 래퍼는 그대로 유지된다 |
| 모드 ON에서 래퍼 안의 **cross-origin** 링크로 이동 | handoff — top을 그 URL로 보내고 같은 폭으로 재수립(S6) |
| **재수립**이 연속 2회를 넘거나 직전 재수립 URL로 되돌아옴 | 리다이렉트 핑퐁·frame-busting으로 보고 다이얼로그 → [확인] 시 모드 해제 + 이슈 idle. handoff가 아니라 재수립을 세야 frame-busting까지 한 그물에 든다 |
| 모드 ON에서 녹화 중 handoff 발생 | 로그는 초기화되지만 탭 녹화 스트림·30s Replay 프레임 버퍼는 탭 단위라 두 사이트를 이어 담는다(오늘의 주소창 이동과 동일). 비침습 토스트로만 알린다 |
| 래퍼 안에서 `window.top !== window.self`로 frame-busting하는 페이지 | 래퍼가 top으로 리다이렉트하거나 동작이 달라진다. top이 곧장 커밋되므로 재수립 → 또 탈출이 반복될 수 있고, 루프 가드가 이를 받아 모드를 해제한다 |
| 사용자가 래퍼 좌우 여백을 드래그해 범위 캡처 | rect를 래퍼 영역으로 **클램핑**한다. 여백이 결과에 안 들어간다 |

## 성공 기준

1. `전체` 상태에서 **기존 e2e 전 스위트가 무변경으로 green**이다. (`e2e/capture-modes-layout.spec.ts:32-45`의 idle 버튼 정확 집합 단언 포함)
2. `390` 선택 후 페이지의 `window.innerWidth === 390`이고, `matchMedia("(max-width: 767px)").matches === true`다.
3. 모드 ON에서 같은 `console.log` 1회 호출이 로그 탭에 **1건**만 나타난다.
4. 모드 ON에서 캡처한 이슈의 재현 환경 `Viewport` 행이 `390×<창높이>`다. **영상·30s Replay로 만든 이슈도 마찬가지다** — 이 둘은 `getTopViewport`를 안 쓰므로 별도 교체 없이는 브라우저 폭이 남는다. element·screenshot·freeform은 e2e로, **영상·30s Replay는 단위(값 전달·null 폴백) + 수동 체크리스트로** 닫는다.
5. 모드 ON에서 `capture-method-fullpage` 버튼이 `aria-disabled`이고, 눌러도 캡처가 시작되지 않는다. (조용한 1타일 성공이 절대 발생하지 않는다)
6. 가용 폭보다 넓은 프리셋이 `aria-disabled`이고, 사이드패널을 좁히면 사용자 조작 없이 활성화된다.
7. `X-Frame-Options: DENY` 응답을 주는 테스트 페이지에서 3초 안에 원본 화면이 복원된다. 모드 유지 중 그 페이지로 이동한 경우에도 같다.
8. 모드 ON에서 래퍼 안의 cross-origin 링크를 누르면 top URL이 그 사이트로 바뀌고 래퍼가 같은 폭으로 다시 서며, 그 사이트의 로그가 1벌만 쌓인다.
9. 모드 ON에서 element 캡처의 `contextSelector` 확장이 모드 OFF와 같은 조건으로 동작한다(조상 컨테이너가 게이트 3개를 통과하면 확장된다).
10. `pnpm typecheck` + `pnpm test` 통과.

## 수용된 잔여 위험

PRD에 명시적으로 남긴다 — 구현 중 이것을 이유로 설계를 되돌리지 않는다.

1. **모드 ON 동안 페이지 내 기존 iframe의 요소 선택 불가.** 2-depth로 밀린다. 사용자 고지(S5)만 한다.
2. **숨겨진 원본 문서와 래퍼 문서가 모드 ON 동안 동시에 실행된다.** timer·WebSocket·polling·자동저장·결제 같은 부작용이 중복될 수 있고 일반적인 페이지를 안전하게 정지시킬 방법은 없다 → 최초 ON 진입 1회 경고로 명시하고 수용한다.
3. **DPR·터치·`pointer: coarse`·UA는 에뮬레이트 불가.** 제품 설명·가이드에서 범위를 "폭 기반 반응형 검증"으로 명시한다.
4. **cross-origin으로 나가는 POST 흐름은 handoff로 재현할 수 없다.** `webNavigation`은 요청 method를 주지 않아 판별조차 못 하고 `chrome.tabs.update`는 GET 재요청이라, SAML POST binding·결제 confirm 토큰류는 깨진다. 다만 handoff를 안 해도(파티션된 로그아웃 화면) 똑같이 깨지고 top으로 나가면 최소한 정상 사이트 문맥으로 복귀하므로 **더 나쁘지 않다**는 근거로 수용한다.
5. **frame-busting 페이지에서 동작이 달라지고, 폭을 나르는 `pending`과 만나면 재로드 루프가 된다.** 래퍼가 `window.top.location = self.location`으로 탈출하면 handoff를 거치지 않고 top이 곧장 커밋되므로 재수립 → 또 탈출이 반복된다. 루프 카운터를 handoff가 아니라 재수립 호출에 건 이유가 이것이다.
6. **탭 녹화·30s Replay의 영상 프레임은 래퍼 좌우 여백을 포함해 찍힌다.** 영상 크롭은 재인코딩 없이 불가. (`Viewport` 메타 값은 이 위험에 해당하지 않는다 — 1차에서 디바이스 폭으로 통일한다.)
7. **래퍼와 숨겨진 top의 로그는 origin으로 구분할 수 없다.** same-origin 불변식의 대가다. 전 프레임 stop ACK 확인 후 래퍼 서브트리만 지정 활성화하고 그 뒤에 store를 clear하므로 실제 수집은 래퍼 트리 1벌이지만, origin 필터는 둘을 못 가른다.
8. **녹화·리플레이 결과물이 handoff를 가로질러 두 사이트를 담는다.** 영상엔 A+B가 이어지는데 로그엔 B만 남는다. 오늘 녹화 중 주소창 이동에서도 같은 비대칭이 나므로 새 축은 아니다 — 토스트로만 알리고 녹화를 끊지 않는다.

## 문서 영향

manifest diff가 0이어도 **새로 관측 가능한 동작이 5개** 생기므로 privacy 문서 갱신은 필수 게이트다(30s Replay가 이 검사를 빠져나가 심사 탈락한 전례가 있다 — `CLAUDE.md:131`).

| 새 동작 | 성격 |
|---|---|
| 같은 URL 재로드 | 페이지 요청이 1회 더 발생 (모드 진입·해제 양쪽) |
| cross-origin 이동 시 탭 전체 재이동(handoff) | 사용자가 클릭한 링크 목적지로 **탭이 통째로** 이동하고 같은 URL 요청이 1회 더 발생 |
| 쿠키 재전송 | 재로드에 수반 |
| 원본 문서 은닉 | 페이지 DOM에 스타일·iframe 삽입 |
| 프레임 단위 로그 수집 대상 변경 | 수집 주체가 top → 래퍼 |
| 에뮬레이트된 화면 캡처 | 스크린샷 내용이 실제 브라우저 표시와 다름 |
